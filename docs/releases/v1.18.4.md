# Sitting Duck v1.18.4

**Release date:** 2026-11-10

One change. `ast_select` and `ast_select_from` no longer pay about 12 s of
DuckDB v2.0 planner time per call. **Output is unchanged**, and the equivalence
section below says how that was established.

**This release requires DuckDB 2.0**, unchanged from v1.18.3. The `duckdb`
submodule pin is still `d54cbbe3` (v2.0.0). No API changed shape. Only
`src/sql_macros/css_selectors.sql` and the header generated from it change.

## This release changes no output value

v1.18.3 changed nine. This one changes none, which is the point of it.

## The fix

Ten pseudo-class arms were correlated subqueries inside one `CASE` in the
`matched_raw` CTE: `:last-child`, `:calls`, `:called-by`, `:is-called`,
`:is-referenced`, `:match`, `:contains`, `:in-scope`, `:precedes` and
`:follows`. Each arm was planned per row of the outer query.

They are now computed once, uncorrelated, into a `pc_hits(pc_id, file_path,
node_id)` CTE. `matched_raw` probes that CTE with one `LEFT JOIN`.

The macro did not get smaller. It is the correlation that cost the time, not the
size of the statement.

## Where the time was

Measured on `build/release`, DuckDB `v2.0.0-dev88609` (source id `d54cbbe3df`),
with `-no-agent` and `SET threads=1`. Every timing is a fresh process, run under
Slurm on a 36-core machine.

`ast_select_from` was truncated at successive CTEs, on a table of `simple.py`:

| the final statement reads | time |
|---|---|
| `sel_props` — all parsing, all 13 validations | 0.81 s |
| `matched_base` | 1.19 s |
| `matched_raw` | 16.1 s |
| `matched_raw`, with only the pseudo-class `NOT EXISTS` | 13.5-13.9 s |
| the same, with that `CASE`'s correlated arms removed | 1.25 s |

`PRAGMA profiling_mode='detailed'` gives `planner.total_time` of 12.41 s with
the correlated arms, against 0.42 s without them. Binding stays under 60 ms
throughout.

The cost was **constant in the input** — 16.5 to 17.9 s across four selectors,
on 110 nodes and on 28,785 nodes. It was **superlinear in the number of
correlated arms**: removing the four arm groups saved 8.9 + 6.3 + 5.6 + 5.9 s
against a 12.6 s total.

## The measured result

Two sets of numbers, because a macro loaded with `.read` is not the shipped
artifact.

**One binary, the old macro and the new macro each loaded with `.read`, two
interleaved rounds:**

| | v1.18.3 | v1.18.4 |
|---|---|---|
| `ast_select_from(t, 'function_definition')`, `simple.py` | 17.42 / 17.25 s | 2.36 / 2.32 s |
| `ast_select('simple.py', 'function_definition')` | 19.24 / 19.70 s | 3.12 / 2.90 s |
| `src/*.cpp` (93,675 nodes), `.call:in-scope(function_definition)` | 771 / 431 s | 3.2 / 3.4 s |
| `css_selectors_multilang.test` alone | 2909.9 s (an older session) | 417.7 s |

**The built-in macro, compiled into a build whose `src/` is identical to this
tag** (`git diff c2a3863 -- src` is empty in that worktree), DuckDB
`v2.0.0-dev88614`, same source id, measured 2026-11-10 UTC:

| call | time |
|---|---|
| `ast_select_from(t, 'function_definition')` | 2.366 / 2.290 s |
| `ast_select('simple.py', 'function_definition')` | 2.928 / 2.922 s |

**The 93,675-node case was EXECUTION, not planning.** The correlated arms ran as
always-on joins, and one of them grew a 37.4M-row `CROSS_PRODUCT` inside a
delim-join CTE on a 28k-node file.

On that large table, `PREPARE` with constant arguments did **not** isolate
execution. Each `EXECUTE` cost about one re-plan, unlike the 0.2 s `EXECUTE`s
measured on `simple.py`. The cause of that difference is unknown.

## What this leaves

About **2.3 s per call**, against a 1.25 s floor for the rest of the macro and
about 0.2 s of execution. That remainder is the case for
`tracker/features/046`, the C++ selector engine, which is re-judged on these
numbers.

The upstream planner regression on correlated subqueries is itself unchanged:
[`duckdb/duckdb#26036`](https://github.com/duckdb/duckdb/issues/26036), open and
labelled `reproduced`. There is still **no minimal upstream repro**. A synthetic
statement with 32 correlated arms over a base table plans in 73 ms.

Two approaches were tried with no effect: `MATERIALIZED` on the hub CTEs, where
`EXPLAIN` confirms that the keyword survives macro expansion; and one
`NOT EXISTS` per arm, which measured 1.4 to 2.4 s at load 20 and is
unconfirmed.

## Equivalence

**`EXCEPT ALL` in both directions, the old macro against the new, over 100
selector cases.** The cases cover every `test/sql` selector that uses a changed
arm, plus negated, glob, alias, nested-class, anonymous-class and row-returning
`:match` forms, and two cases that return different rows from one arm, to
exercise `pc_id`.

| | count |
|---|---|
| rows on each side | 7776 |
| differing rows, either direction | **0** |
| cases that produce output | 94 of 100 |
| cases that error identically | 6 |
| cases that return rows | 78 |
| cases empty on both sides | 16 |

**The denominator is skewed, and this is the limit of the check.** One case
returns 3461 of those 7776 rows. The other 93 cases return 4315 rows between
them, and the median case returns 4 rows. So "0 differing rows over 7776" is
weaker evidence for the small cases than the total suggests. The 6 error cases
raise byte-identical messages.

All 36 `test/sql` files that call `ast_select` pass with the same assertion
counts as a build of unchanged `main`.

## A claim this release had to correct about itself

The GitHub release body for this tag states that "the v2.0 CI leg still runs
with `skip_tests`". That is wrong, and it is wrong in the direction that
weakens the release's own evidence.

`.github/workflows/MainDistributionPipeline.yml:619` defines
`Build extension binaries (v2.0 test coverage)` and carries the comment
`Deliberately NO skip_tests: running the tests is the entire point.` That leg is
job 129552193217 in the table above, and it ran 182 tests. The leg that does
carry `skip_tests` is the one pinned to the `v2.0-cyanoptera` branch of
extension-ci-tools, which compile-checks rather than tests.

## Known issues

Unchanged from v1.18.3, except that the `ast_select` planning cost is largely
fixed here. None of the rest is addressed.

- **About 2.3 s per `ast_select` call remains** (`tracker/bugs/040`, last
  section). See "What this leaves" above.
- **#323**, **#324**, **#317**, **#320**, **#322** — the five defects that
  v1.18.3 filed. All open.
- **#276** and **#288** — `ast_definitions()` both duplicates a name that has a
  wrapper node, and misses a name bound by the bare-name hook.
- **#186** — every language's root node is unnamed, in all 27 of them. Decided
  in v1.18.3, not implemented.
- **116 documented examples read an unbounded tree** (`tracker/bugs/055`).
- **Attribute filters inside `:has(...)` are not supported** (#150).
- **`:precedes(type)` and `:follows(type)` accept a node type that does not
  exist** and return 0 rows rather than refusing.
- **`:exported` does not hold for Dart** (`tracker/bugs/056`).
- **The conformance kit runs nowhere in CI.**

## Upgrading

Drop-in from v1.18.3. No output value moves, and no API changed shape.

A caller that worked around the planning cost may want to undo the workaround.
`PREPARE` with constant arguments still amortizes, and it is no longer worth
the loss of a varying selector.
