## Shape A is larger than #288's example

#288 shows bare parameters and for-loop targets. Measured, one 22-line Python
file has ten such names, across five binding constructs:

```
identifier         x            <- bare parameter
identifier         zz           <- for-loop target
as_pattern_target  handle       <- with ... as
as_pattern_target  e            <- except ... as
identifier         a, b         <- tuple assignment targets
identifier         self, conn   <- bare parameters
attribute          self.cache   <- dotted tuple target
attribute          self.size    <- dotted tuple target
```

All ten have `is_name_definition(flags)` true and `is_definition(semantic_type)`
false, so all ten are absent from `ast_definitions()`. The construct list is the
same list #64 calls "likely missing", which is why #64 closes as superseded.

## Drift from the issue text

1. **#273's mechanism is narrower than reported.** The right-hand side leaks
   into `name` only when the first child after a non-identifier target is a bare
   identifier.

   | source | reported name |
   |---|---|
   | `self.db = conn` | `conn` — the RHS |
   | `obj.attr = 5` | empty |
   | `arr[0] = 6` | empty |

   So this is `FIND_IDENTIFIER` scanning past the target into the RHS, not a
   general "name comes from the RHS" rule. A fix that stops the scan at the
   target closes all three rows at once.

2. **#140a has got worse, and the issue's number no longer holds.** The issue
   records 22 of 95 `command` nodes named. Measured today it is **0 of 95**.
   `command_name` exists, 95 of them, and is also unnamed. The command word is
   present and named on `word` nodes, 161 of them. So the target is
   `command_name`'s `word` child, and the 22 in the issue text should not be
   used as a baseline. **Conflict resolved, by reading the commit that caused
   it.** It regressed after the issue was filed, and deliberately. Commit
   `28c61fd` ("#139 IS_CONSTITUENT", 2026-09-14) changed `command` from
   `EXECUTION_STATEMENT, FIND_IDENTIFIER` to `COMPUTATION_CALL, NONE`, and its
   message says why: "Left UNNAMED deliberately: correct command-name binding
   needs machinery tracked in #140; naming it wrongly (FIND_IDENTIFIER picked
   `+%s`) would defeat the #89 'can't answer -> raise, never silent empty'
   guard." So the issue's 22 were NAMED BUT WRONG, not a different set --
   `+%s` is an argument of `date +%s` in test/data/call_extraction/calls.sh,
   because argument words are direct children of `command` while the command
   name sits inside a `command_name` wrapper. #140a is therefore not a
   FIND_IDENTIFIER repair; it is the binding that commit deferred.

3. **#140b: neither Go node is usable on its own.** `type_spec` carries the name
   `Point` but has no role flag and no definition semantic type.
   `struct_type` has a definition semantic type but an empty name. The fix must
   join them, and choosing either node alone leaves the other half missing.

4. **#277's name is an empty string, not NULL.** The issue says `<NULL>`. The
   macro filters `name IS NOT NULL AND name != ''`, so it drops either way, but
   a test asserting NULL would be wrong.

5. **#283's pointered form does not parse into a function.** Three of four
   `function_definition` rows come back for four functions.
   `pointered(Args*... args)` produces no row at all, so it is not a parameter
   defect there — the function itself is invisible. That makes it the most
   serious of the three qualified forms, and possibly a separate defect.

6. **Go `a, b := 2, 3` is one node binding two names.** Both
   `short_var_declaration` rows carry an empty name. Same shape as JS
   `let a = 1, b = 2`, where the container claims only `a`. A single-valued
   `name` column cannot express either, so the release has to state what it does
   rather than pick one name.

## #140b, as landed — and the two oracles it corrected

Landed as `b20ef61` (test, verified red), `527f008` (the oracle corrections)
and `3554016` (the fix).

**The generality question Teague set, answered.** His condition was "make sure
it's reasonably general beyond just Go. If it's useful and general we can add it
as a flag." Measured, the condition does not apply: **`IS_CONSTITUENT` already
exists**, added by `28c61fd` for #139, and it is already set on 50 node types
across 17 languages. Nothing is minted. Applying it to two more node types is
configuration, not a taxonomy change.

The shape itself is NOT general. A survey of every node with a `DEFINITION_*`
semantic type, `name_strategy='none'`, not syntax-only and not already a
constituent returns about 51 rows, and they fall into three groups:

| group | count | is it "an unnamed body duplicating its named declaration"? |
|---|---|---|
| root / file nodes (`program`, `source_file`, `module`, …) | ~25 | No. Top-level construct. This is #186's subject. |
| genuinely anonymous constructs (kotlin lambdas and initializers, typescript call/construct/index signatures, cpp `default_method_clause`, java `static_initializer`, graphql schema nodes) | ~24 | No. They duplicate no named parent. |
| **go `struct_type`, `interface_type`** | **2** | **Yes.** |

And the fallback Teague named is unavailable: the `Class` refinement is 2 bits
and `REGULAR`, `ABSTRACT`, `GENERIC`, `ENUM` are all assigned
(`src/include/node_config.hpp:242-247`).

**The cost, on the record.** Every one of the 50 existing constituents is
context-FREE: a string's content is always a sub-part. Go's `struct_type` is
context-DEPENDENT — a sub-part in `type Pair struct{}`, the whole construct in
`var anonymous struct{}` and in `struct{}{}`, which is how Go spells a set
element. A stored per-node-type bit cannot express that, and `28c61fd`
deliberately chose a stored bit over a structural query. So the two anonymous
forms leave `.class`. Section 4 of the test pins the loss.

**Measured before and after**, over every committed Go fixture:

| | before | after |
|---|---|---|
| `ast_definitions()` class rows for Go | **0** | **11** |
| `.class` rows over the #140b fixture | 4, all with an empty name | 7, all named |
| `ast_resolve_entity('Read').qualified_name` | `F[Read]` | `C[Reader] F[Read]` |

### Two oracles I put on record and had to correct

1. **The flag byte reads 30, not 14.** `30 = IS_EXPORTED (16) | IS_SCOPE (8) |
   NAME_DEFINITION (6)`. The exported bit comes from Go's capitalization rule at
   parse time, not from the `.def` entry, and every name in the first fixture
   was capitalized, so the bit was invisible to the prediction. `type
   unexported int` is now the control: 14 against its siblings' 30.

2. **The body must not keep `IS_SCOPE`.** With the flag on both nodes, Go had
   two stacked class scopes, and `scope.class` for the field `First` pointed at
   the unnamed `struct_type` while `.class#Pair` matched the `type_spec`:

   ```
   .variable:in-scope(.class#Pair)   -> EMPTY
   .class#Pair .variable             -> First, Second
   ```

   Two forms of one question disagreeing is #166's defect. No other language
   gives a type BODY a scope — java `class_body`, typescript `interface_body`,
   rust `field_declaration_list` are all flags 0 — so removing it matches the
   house convention. The only measured loss is that an anonymous struct's field
   reports `scope.class = NULL` instead of an unnamed node id. Its
   `qualified_name` is unchanged.

**Generated artifacts.** A `.def` change needs
`python3 docs/scripts/generate_language_reference.py` committed with it, and
`scripts/check_def_type_tables.py` run first. Note the generator FLATTENS every

(`generate_language_reference.py:113-119`), so a long rationale belongs in a
plain `//` block above the doxygen comment, not inside it.

## #140c, as landed — and the third pin nobody had listed

Landed as `d64e561` (test, verified red) and the fix commit beside it.

**The defect, measured.** `languages/java/java_types.def:73` gave
`import_declaration` the NODE_TEXT strategy, so its name was the whole
statement: `import java.util.List;`, keyword, spaces and semicolon included.
Over `test/data/**/*.java` that is 44 nodes, and `.import[name^="java"]`
matched **0 of 44** while `[name*="java"]` matched **44 of 44**. A prefix query
over an import path — the normal way to ask what a file depends on — could not
be written at all.

**#140a's technique does not transfer.** Bash's `command` read the grammar's
required `name` field. `grammars/tree-sitter-java/src/node-types.json` gives
`import_declaration` `"fields": {}` — it has **no named fields**. So the
binding scans children by TYPE. The rule is

    import_declaration: 'import' ('static')? _name ('.' asterisk)? ';'

and `import`, `static`, `.` and `;` are all anonymous, so the NAMED children
are exactly `_name` (`identifier | scoped_identifier`) and the optional
`asterisk`. Scanning named children is therefore exact, not a heuristic.

**Two decisions, both asserted rather than assumed.**

1. A wildcard import KEEPS its star: `import java.io.*;` is named `java.io.*`.
   Teague settled this: "I think your default is right. I could even see it
   named `*`." Read as "keep the star", not "name it bare `*`", because a bare
   `*` would make the issue's own selector miss every wildcard import. The
   `scoped_identifier` child holds only `java.io`, which nothing distinguishes
   from a single-type import of a class named `io`.
2. `static` is DROPPED. `name` is a path in every other language, and the
   keyword stays in the node's own text.

**No new fixture, because the right glob already exists.**
`test/sql/conformance/call_naming_conformance.test:186` globs
`test/data/languages/java/*`, so a fixture dropped there would move a
conformance count for no reason. The corpus holds three of the five grammar
shapes, measured:

| shape | count |
|---|---|
| `import scoped_identifier ;` | 40 |
| `import scoped_identifier . asterisk ;` | 3 |
| `import static scoped_identifier ;` | 1 |

The missing two — `import static <path>.*;` and a bare `identifier` — are
supplied from source text through `parse_ast()`, which takes a string rather
than a path. That is the cheapest way to test a grammar shape the corpus lacks,
and it adds nothing to any glob.

`test/sql/conformance/capability_declarations.test:293` pins

## #283, as landed — and the ruling that widened it

### The issue's three-form table was six forms, and one of them was already right

Measured on the release build at `b3abb6d` (blq `duckdb:208`, `duckdb:212`):

| source | name before | type before | verdict |
|---|---|---|---|
| `plain(Args... args)` | `args` | `Args...` | right |
| `qualified(const Args&... args)` | *empty* | `const...` | both wrong |
| `rvalue(Args&&... args)` | *empty* | `Args...` | name wrong |
| `unnamed(Args...)` | *empty* | `Args...` | **right** — not in the issue |
| `qualunnamed(const Args&...)` | *empty* | `const...` | type wrong — not in the issue |
| `tmpl(std::vector<Args>&&... args)` | *empty* | `std::vector<Args>...` | name wrong — not in the issue |
| `pointered(Args*... args)` | no `function_definition` row, plus ERROR nodes | — | unparseable |

`unnamed` matters: it is the one case where the old "first non-declarator child
plus `...`" rule happens to be correct, so any rewrite had to not regress it.

### The #140a field technique DOES transfer here

#140c recorded that java's `import_declaration` has `"fields": {}`, so
`ts_node_child_by_field_name` was unavailable and a named-child scan was needed.
The opposite holds for C++. `grammars/tree-sitter-cpp/grammar.js:463-478`:

```js
variadic_parameter_declaration: $ => seq(
  $._declaration_specifiers,
  field('declarator', choice(
    $.variadic_declarator,
    alias($.variadic_reference_declarator, $.reference_declarator),
  )),
),
variadic_declarator: $ => seq('...', optional($.identifier)),
variadic_reference_declarator: $ => seq(choice('&&', '&'), $.variadic_declarator),
```

So there is a required `type` field, a required `declarator` field, and the
declarator is one of exactly two shapes. The identifier is at depth 1 or 2 and
never deeper. "Search at any depth" was not needed; the walk is exact.

The lesson is that the technique is per grammar and per node, not per language.
Neither "fields exist" nor "fields do not exist" is the general case, so the
answer comes from `node-types.json` every time.

### The pointer pack has a grammar line, not an inference

The `declarator` choice above offers `variadic_declarator` and
`variadic_reference_declarator` only. There is no pointer alternative. Four
spellings were measured — in a struct, with a space, with a different return
type, and with the star after the ellipsis — and every one produced ERROR nodes
(`duckdb:209`). So `Args*... args` is unparseable by construction. It is not an
extractor defect and no adapter change can reach it. The grammar is NOT patched
for it: that is a large change nobody asked for.

### Teague's ruling widened the issue

The first plan matched the house convention and took the type from the `type`
field plus `...`, which would have given `args : Args...` for every form. The
reply was:

> "What about adding the qualifier to the other types to match Args. int& is
> different than int in my opinion."

Measured, the convention it would have matched is this (`duckdb:210`):

```
void f(const int& a, int&& b, int* c, const std::vector<int>& v)
  ->  a:int   b:int   c:int   v:std::vector<int>
```

Every qualifier dropped, for every ordinary parameter. So the ruling is a change
to the C++ parameter convention as a whole, not only to packs. It was taken as
an instruction.

Both halves had to land in ONE commit. A column where a pack keeps `const` and
an ordinary parameter drops it is worse than one that is uniformly bare, and
that inconsistency is exactly what the ruling objects to.

### The rule: C++'s own abstract declarator

A parameter's type is its declaration with the NAME removed. Removed with it:
the specifiers that are not part of a type, which `node-types.json` gives as
`attribute_declaration`, `attribute_specifier`, `ms_declspec_modifier` and
`storage_class_specifier`. `type_qualifier` is kept, because `const` IS part of
the type.

Excising the name beats taking the span BEFORE the name. That is what makes the
hard rows right:

| declaration | span-before-name | excision | correct type-id |
|---|---|---|---|
| `const int& a` | `const int&` | `const int&` | `const int&` |
| `int arr2[10]` | `int` | `int[10]` | `int[10]` |
| `void (*fp)(int)` | `void (*` | `void (*)(int)` | `void (*)(int)` |
| `int (&arr)[3]` | `int (&` | `int (&)[3]` | `int (&)[3]` |

All fifteen predicted type strings were confirmed on the first run of the test
after the build: 74 assertions, no adjustment.

### The pack stopped being a special case

`ExtractCppVariadicParameterDeclaration` is now four lines over the two shared
helpers. The `...` needs no concatenation, because it is in the source text and
excising the name leaves it in place. This is the structural spirit #283 asked
for, reached by a different route than the one it suggested.

### The same rewrite repaired four name losses nobody had reported

`ExtractParameterDeclaration` descended ONE level into a declarator, so the
declarator-id of a nested shape was never reached. Measured before
(`duckdb:212`), all four reported an EMPTY parameter name:

| declaration | name before | type before |
|---|---|---|
| `int** pp` | *empty* | `int` |
| `void (*fp)(int)` | *empty* | `void` |
| `int (&arr)[3]` | *empty* | `int` |
| `const char* const* argv` | *empty* | `char` |

This was not extra scope. The qualifier rule needs the name's byte range to
excise it, so a lookup that returns nothing would have put the NAME INSIDE the
type — `int** pp` would have had the type `int** pp`. Fixing the names was the
precondition, not a bonus. The advisor caught this before any code was written.

The walk is bounded by fields, not by a search: `pointer_declarator`,
`array_declarator` and `function_declarator` each carry a `declarator` field,
and a function_declarator's own parameter list is a SEPARATE `parameters`
field. So following the field can never descend into a function pointer's
parameters and mistake one of those for the name.

### Three defects found while measuring, none of them fixed here

1. **A C++ function with a default argument reports ZERO parameters.**
   `void dv(const int& x = 0)` and `void dv2(int y = 3, double z = 1.5)` both

   This is the #220 shape for a fourth time: a dead branch naming a node the
   grammar does not emit, with no failing test.

2. **A C++ lambda reports zero parameters, variadic or not.**
   Both `[](auto&&... xs){}` and `[](int a, double b){}` return an empty list
   (`duckdb:210`). Not pack-specific, so not the same cause as #283. Cause not
   established.

3. **C and C++ disagree on the same source.** C already keeps one level of
   pointer: `const char* s` reads `char*` in C and read `char` in C++
   (`duckdb:212`). After this change C++ gives `const char*`, so they still
   disagree, in the other direction. `c_native_extractors.hpp` has its own
   parameter extraction and is untouched here.

Return types and variable types are also still bare: `const T& get()` has the
signature_type `T` (`duckdb:212`). The ruling's principle reaches them, and
this change does not. That is deliberate and vetoable, not an oversight.
