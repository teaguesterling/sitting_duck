# Sitting Duck v1.16.0

**Release date:** TBD

Byte-exact source reconstruction, a native `COPY ... TO (FORMAT ast)` writer,
YAML as a 28th language — and a family of classification bugs that had one
shape in common: a declaration that could never match a node, or a value that
silently wrapped, so the answer looked reasonable and nothing said otherwise.

Several fixes **change query results**. If you pin semantic types or node
counts, read "Output changes" before upgrading.

## New

- **Byte-exact unparse** (#174, `047`). `ast_unparse_exact(path)` returns the
  original bytes of a file reconstructed from its AST rows — not a formatted
  approximation. It either reproduces the source exactly or refuses; there is
  no normalising mode. **27 of 27 tree-sitter languages** round-trip
  byte-identically, up from 0 — 26 when the work landed, plus YAML, verified
  for this release.

  `duckdb` is out of scope: its tree is an AST rather than a CST, so there are
  no gaps to splice (#197, `047` "4b part 1").

  | | |
  |---|---|
  | `ast_unparse_exact(path, language := NULL)` | by path, or a glob matching exactly one file |
  | `ast_unparse_exact_from(ast_table, files)` | from a node table you already have |
  | `ast_unparse_exact_code(source_code, language)` | from a string |
  | `ast_unparse_exact_splice(ast_table, blob_table, ...)` | the underlying per-leaf splice |

  The completeness guard is `row count = root.descendant_count + 1`. It exists
  because a filtered subset would otherwise be absorbed into the splice's gaps
  and produce byte-exact-looking output that proves nothing.

- **`COPY ... TO (FORMAT ast)`** (#174). The writer form of the above:

  ```sql
  COPY (FROM read_ast('in.py', source := 'full', peek := 'none'))
  TO 'out.py' (FORMAT ast);
  ```

  Implemented as a bind-time statement rewrite over the same splice, so the
  writer and `ast_unparse_exact` cannot disagree.

- **Byte offsets.** `read_ast(..., source := 'full')` now carries
  `start_byte` / `end_byte`, which is what makes exact slicing possible
  instead of approximate.

- **YAML, the 28th language** (#227). The adapter, the `YAMLAdapter` class and
  a 43-entry type table had existed for a long time while YAML was absent from
  `cmake/BuiltinLanguages.cmake`, had no generated parser, and had its
  extension mappings commented out. It is now registered, covered by the
  conformance kit, and accepts `.yaml` / `.yml`.

  Its parser is ABI 13 rather than 15. The runtime loads that
  (`TREE_SITTER_MIN_COMPATIBLE_LANGUAGE_VERSION` is 13) but the *compile* needs
  the ABI-13 header the grammar shipped with, and its external scanner is the
  only C++ one in the tree. The grammar cannot be regenerated by the
  parser-generation CLI (#233).

## Output changes

Read this section if you pin semantic types, flags or node counts.

- **Structural counts no longer wrap** (#212). `descendant_count`,
  `children_count` and `depth` were computed as `uint32` and then stored
  through `uint16`/`uint16`/`uint8` mirrors, and those mirrors are what the row
  emitters wrote. Measured:

  | field | fixture | before | after |
  |---|---|---|---|
  | `descendant_count` | 100 001-node tree | 34 464 | **100 000** |
  | `children_count` | 70 000 sibling statements | 4 464 | **70 000** |
  | `depth` | 3 000-term expression | 255 | **3 003** |

  The serious half was silent: `node_id BETWEEN x AND x + descendant_count` —
  the O(1) subtree idiom the docs recommend — returned **34 465 of 100 001
  rows with no error**. Any file whose AST exceeds 65 536 nodes gave wrong
  answers from that idiom and correct ones below the threshold.

- **Anonymous keyword tokens stop impersonating their construct** (#215, #208).
  A tree-sitter grammar can use one type string for two symbols: ruby `if` is
  both the if-statement rule and the bare `if` keyword. The config map was
  keyed on the string alone, so the keyword inherited the statement's
  classification and every construct was counted twice. 27 collisions across
  7 languages now declare the anonymous half separately. Ruby control flow was
  exactly double-counted — 32 nodes where 16 exist.

- **TypeScript type keywords are types, not literals** (#222). `string`,
  `number` and `object` in type position were classified `LITERAL_STRING` /
  `LITERAL_NUMBER` / `LITERAL_STRUCTURED`. They are now `TYPE_PRIMITIVE`.
  `typescript_types.def` had always said so; the declaration was dead, because
  `javascript_types.def` is `#include`d first and an `unordered_map`
  initialiser list is first-wins.

  The same fix activates five native strategies TypeScript had declared and
  never used: `method_signature`, `property_signature`, `required_parameter`,
  `type_annotation` and `type_identifier` now produce signature data.

- **Refinements added to JavaScript** (#222). A JS `switch` is multiway and a
  JS `break` is a BREAK jump; both were plain. Selector behaviour is
  unchanged — `base_type` masks the low 2 bits — but the raw `semantic_type`
  byte differs.

- **315 declarations deleted for node types no grammar can emit** (#232), 8%
  of all declarations across 23 languages. These were unreachable by
  construction, so no node's classification changes — but `ast_type_map()`
  loses those rows, and anything reading it as a capability list sees a
  smaller, truer vocabulary. css's call-type count drops from 8 to 1, because
  seven of the eight were CSS *function names* (`calc`, `rgb`, `hsl`, ...) and
  the grammar has no such symbols.

- **`duckdb` adapter structural columns** (#197, #205). The DuckDB-parser
  adapter reported `children_count = 0` for every node, so every node looked
  like a leaf. All four structural columns are now derived from `parent_id`.

- **Keyword operators classified against the convention the taxonomy already
  implied** (#231). `spec/taxonomy/taxonomy.yaml` enumerates keyword operators
  in the semantic-type descriptions themselves — `OPERATOR_LOGICAL` names
  `and`/`or`/`not`, `OPERATOR_COMPARISON` names `is`/`in`/`not in` — and those
  were already compliant everywhere. The unary type-query, cast and
  operator-declaration family had no rule, and five tokens were filed under
  the operator kind without one. Nine declarations moved:

  | token | languages | before | after |
  |---|---|---|---|
  | `typeof` | javascript, typescript | `OPERATOR_LOGICAL` | **`TYPE_REFERENCE`** |
  | `of` | javascript, typescript | `OPERATOR_COMPARISON` | **`FLOW_LOOP`** |
  | `only` | css | `OPERATOR_LOGICAL` | **`METADATA_DIRECTIVE`** |
  | `operator` | swift | `OPERATOR_ARITHMETIC` | **`DEFINITION_FUNCTION`** |
  | `as` | rust, kotlin, swift | `COMPUTATION_CALL`, `OPERATOR_COMPARISON` ×2 | **`TYPE_REFERENCE`** |

  `of` was the widest error and was not in the filed issue: loop `in` is
  `FLOW_LOOP` in six languages, and the `of` token appears only under
  `for_in_statement`. `in` itself is **unchanged** — in JavaScript the same
  token spells both the loop and the membership test, one declaration covers
  both, and `OPERATOR_COMPARISON` is what the spec prescribes for the
  comparison form.

  **`.class` selectors are unaffected; `[semantic=...]` selectors are not.**
  All nine tokens are `IS_SYNTAX_ONLY`, and a class filter excludes syntax-only
  nodes, so `.logical` never matched `typeof` and `.type` does not match it now.
  The `[semantic=...]` attribute selector has no such guard, so
  `[semantic=TYPE_REFERENCE]` now matches `typeof`, `[semantic=FLOW_LOOP]` now
  matches `of`, and `[semantic=LOGICAL]` no longer matches `typeof`. On one
  6-line fixture `.loop` returns 2 while `[semantic=FLOW_LOOP]` returns 5 — the
  difference being the syntax-only keyword tokens. If you select by
  `[semantic=...]`, re-check those predicates.

  One capability count moves with it: rust declared `as` as `COMPUTATION_CALL`
  with a `node_text` name strategy, so a cast keyword was counted as a
  call-semantic type that extracts a callee name. Rust's call-semantic type
  count drops from 3 to **2** (`call_expression`, `macro_invocation`) — the
  declared capability was inflated by a token that is not a call.

  Left deliberately alone, and pinned by test so they read as decisions:
  `sizeof` stays `OPERATOR_ARITHMETIC` (it yields a number); python `as` stays
  `METADATA_ANNOTATION` (it binds a name, never a cast); kotlin `operator`
  stays `METADATA_ANNOTATION` (a modifier on a declaration, not the
  declaration); `is` and `instanceof` stay `OPERATOR_COMPARISON` (a type test
  yields a boolean). The taxonomy spec goes `1.0.0` → `1.0.1` — documentation
  only, generated C++ byte-identical. `OPERATOR_UNARY` was not an option: all
  64 base codes are allocated and the operator kind is full, so adding one is
  a MAJOR taxonomy break.

## Fixes

- **Unknown semantic classes raise** (#188). `.frobnicate` returned 0 rows,
  indistinguishable from a valid class that matches nothing. The selector
  vocabulary is now enumerable (`ast_semantic_aliases()`), documented, and an
  unknown class errors.
- **Declared call targets bind** (#209). `FIND_CALL_TARGET` was declared and
  not wired for java constructor calls, lua dotted module calls and kotlin
  constructor invocations, so `.call#X` silently missed them.
- **Duplicate type keys** (#208). A `raw_type` declared twice silently dropped
  one entry, so ruby class definitions were double-counted.
- **Leaf text** (`047`). A named leaf with no text-producing name strategy
  unparsed to its own *type name* instead of its text — `comment` became the
  literal word "comment". 348 gaps were derived from the grammars (not
  hand-listed, after #184's lesson); **134 are closed, 214 outstanding**.

## Internal

Not user-visible, but it explains the size of the diff: a conformance kit with
a recorded baseline and eight negative controls; four derivation scripts that
fail on a regression (unreachable declarations, anonymous-token collisions,
shadowed declarations, leaf-text coverage); the taxonomy tables generated from
`spec/taxonomy/taxonomy.yaml`; and two kinds of dead code removed — **1 846
lines** across six files that no build configuration had ever compiled,
including a second, contradictory copy of the semantic taxonomy (#196), and
**315 declarations** for node types no grammar can emit (#232).

## Known issues

- **The conformance kit exits 3 on a clean tree, and that is expected.**
  `kotlin`, `lua` and `sql` declare function-shaped native strategies and
  deliver no parameters (#220) — the declaration is unbacked. The full
  baseline is recorded in `tracker/features/044-v2-m1-contract.md`:
  `ok=189 FAIL=3 dirty=1 void=13 UNDECL=5 n/a=13` over 28 languages. A *new*
  FAIL, or a count that moves without an explanation in that table, is a
  regression. This one is not.
- Keyword operators have no taxonomy category, so their classification is
  inconsistent across languages — `as` has four different ones (#231). No
  selector is affected: the selector engine excludes syntax-only tokens from
  every semantic-class filter.
- YAML's grammar cannot be regenerated by the parser-generation CLI (#233), so
  it is pinned to the parser it shipped and sits at the minimum supported
  tree-sitter ABI.
- `module` scope nodes carry `name = ''`, so `:is-scope(module#x)` can never
  match (#186). Unaffected for `function` and `class`.

## Upgrading

No API removals. Two things to check:

1. **If you compare `semantic_type` or `flags` to pinned values**, re-measure.
   The anonymous-token, TypeScript and refinement changes above all move the
   raw byte for specific node types.
2. **If you read `ast_type_map()` as a vocabulary**, it is smaller and more
   accurate. Entries that could never match a node are gone.

If you relied on `descendant_count` arithmetic over files larger than 65 536
nodes, your previous results were wrong and are now right; nothing needs
changing on your side.
