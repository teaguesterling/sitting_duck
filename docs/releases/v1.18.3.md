# Sitting Duck v1.18.3

**Release date:** 2026-11-09

Nine defects in one class. A name that a reader can see in the source either
never reached the `name` column, or reached it wrong. Each fix has a test that
was verified RED before the fix. Two of the nine were also proved by planting
the defect that the test must catch.

**This release requires DuckDB 2.0**, unchanged from v1.18.2. The `duckdb`
submodule pin is still `d54cbbe3` (v2.0.0). No API changed shape.

## This release changes output

Four of the changes are visible in `read_ast()` and `parse_ast()` output itself,
so they reach every caller and not only `ast_select`. Read this section before
you upgrade.

### 1. C++ arity changes

A defaulted parameter now appears in `parameters`.

| source | was | now |
|---|---|---|
| `void f(int a, int b = 2)` | 1 parameter | 2 parameters |
| `void dv(const int& x = 0)` | 0 parameters | 1 parameter |

Any query that counts C++ parameters sees different numbers. The old numbers
were short, and nothing in the row said so.

### 2. C++ parameter names change where the declarator nests

| source | was | now |
|---|---|---|
| `const std::string& s` | `std::string` (the type) | `s` |
| `int* p` | *(empty)* | `p` |
| `int& r` | *(empty)* | `r` |
| `int (*fp)(int)` | *(empty)* | `fp` |
| `int arr[3]` | *(empty)* | `arr` |
| `int& r = global` | `global` (the default value) | `r` |
| `int = x` | `x` (the default value) | *(empty)* |

The last row is the deliberate direction of the fix. An abstract parameter has
no name, so the column is empty rather than holding a guess.

### 3. Three more C++ nodes now carry parameters

`function_declarator`, `parameter_list` and `lambda_expression` reported no
parameters for every parameter, defaulted or not. A prototype,
`void k(int a, int b = 2);`, now reports its parameters.

One consequence is worth stating. A C++ `function_definition` and its child
`function_declarator` are both `DEFINITION_FUNCTION`. A function therefore
yields two rows that carry the same name, return type and parameter list. Those
rows already shared the name and the return type. `parameters` was the one field
that was still empty.

### 4. C names a function that returns a function pointer

`int (*fp_ret(int a))(char)` reported the name `int`, which is the return type.
It now reports `fp_ret`. This came with #318's shared declarator walk and was
not a separate fix.

### Also changed

Kotlin `primary_constructor` and `secondary_constructor` now deliver parameters
and modifiers where they delivered nothing. Go named types gain a name. Java
import statements gain a path.

The C++ parameter rows moved from the `FIND_IDENTIFIER` name strategy to
`FIND_IN_DECLARATOR`. That moves the `FIND_IN_DECLARATOR` language count from 2
to 3 in `ast_type_map()`.

## Fixes

### An assignment never names its right-hand side (#273, #277)

`FIND_IDENTIFIER` scanned every child for a name. Where a node has a `left`
field, the name belongs to the target.

```
self.path = path     ->  reported `path`, the right-hand side
dx := p.X - other.X  ->  reported nothing
```

`self.path = path` asserted that the right-hand side is defined there. It is a
parameter that is defined elsewhere and only read. Go's
`dx := p.X - other.X` found nothing, because tree-sitter-go wraps `left` in an
`expression_list`, so no direct `identifier` child exists.

The rule now has three branches. The middle branch is why a naive version fails:
descending into `left` without a test returns `self` for `self.path`, because
`self` is the first identifier inside the `attribute` node.

- `left` is a bare name — that name.
- `left` is a `*_list` of exactly one element — descend, then apply the same
  test.
- anything else — no name.

A list of more than one element reports nothing on purpose. `a, b := 1, 2` binds
two names and `name` is one column, so naming the first would be a plausible
wrong answer. An `attribute`, a `subscript` or a destructuring target also
reports nothing, because none of them is a bare name.

**Blast radius, measured.** `FIND_IDENTIFIER` has 292 uses over 206 node types.
Only a node that HAS a `left` field takes the new path. Every such node is
assignment-like: `assignment`, `assignment_statement`, `assignment_pattern`,
`operator_assignment`, `variable_assignment`, `enum_assignment` and
`short_var_declaration`. Ruby's `instance_variable` and `global_variable` stay
out of `IsSimpleNameNodeType`, so `@name = name` reports nothing rather than the
right-hand side.

### Bash command names (#140a)

A bash command name came from the node text. It now comes from the grammar's
required `name` field.

### Go names its type declarations (#140b)

Go spelt a named type with two nodes, and neither was usable alone.

```
type_spec     name='Pair'  EXECUTION_DECLARATION  is_definition=false
struct_type   name=''      DEFINITION_CLASS       is_definition=true
```

`ast_definitions()` filters on `is_definition()` AND `name <> ''`, so Go had
ZERO class definitions. Measured over every committed Go fixture: 0 rows before,
11 after. `.class` returned four unnamed rows and could not tell a caller that
`Pair` exists.

The declaration node now carries the name and the class, which is what every
other language in this tree already does. `type_alias`
(`type Celsius = float64`) is a different grammar node and had no entry in the
Go definitions file, so it fell through to `PARSER_CONSTRUCT` with no name. It
has an entry now.

**A known and accepted cost.** A per-node-type bit cannot depend on context, and
Go's `struct_type` does. It is a sub-part in `type Pair struct{}`, and the whole
construct in `var anonymous struct{}` and in `struct{}{}`. Those anonymous forms
are no longer selected by `.class`. They keep their semantic type, so a
structural query still reaches them. Section 4 of the test pins the loss rather
than hiding it.

### A Java import is named for its path (#140c)

`import java.util.List;` was named for the whole statement. It is now named
`java.util.List`. Measured over `test/data/**/*.java`: `.import[name^="java"]`
goes from 0 of 44 to 44 of 44, and no name now holds a space or a semicolon.

Two decisions. A wildcard import KEEPS its star, so `import java.io.*;` is named
`java.io.*`. The `scoped_identifier` child holds only `java.io`, which nothing
distinguishes from a single-type import of a class named `io`. The `static`
keyword is DROPPED, because `name` is a path in every other language, and the
keyword stays in the node's own text.

### A C++ parameter's type is its declared type (#283)

The convention before this release dropped every qualifier. Measured, it read
`const int& a`, `int&& b` and `int* c` all as `int`. Teague set the new rule:
"int& is different than int in my opinion".

One rule now covers every C++ parameter, variadic or not. The type is the
declaration with the parameter NAME removed, which is C++'s own abstract
declarator.

```
int arr[10]       ->  int[10]
void (*fp)(int)   ->  void (*)(int)
int (&arr)[3]     ->  int (&)[3]
```

Excising the name is what makes those rows right. Taking the span before the
name would have given `int`, `void (*` and `int (&`.

`type_qualifier` stays in the type, because `const` is part of a type.
`storage_class_specifier`, `attribute_declaration`, `attribute_specifier`,
`ms_declspec_modifier` and comments go with the name, because they are not.

### Kotlin constructors deliver their parameters (#263)

`class Person(val name: String, val age: Int)` reported ZERO parameters, and so
did `constructor(a: Int)`. Both declared the native strategy `NONE`, so the
declaration and the delivery agreed, and the conformance kit passed them
correctly.

Java's constructor extractor cannot be delegated to here, for three measured
reasons.

1. `primary_constructor` holds `class_parameter` as a DIRECT child with no
   container, so the existing walk finds nothing. `secondary_constructor` does
   have the container, so it reuses that walk.
2. The default value is a CHILD of `class_parameter`, not a sibling of it. So
   `class P(val x: Int = y)` has two `simple_identifier` children, and the
   reused walk would report the name as `y` — the parameter named after its own
   default.
3. Two helpers on the shared path are wrong for a constructor. One falls through
   to a `Unit` return type, and a constructor has no return type. The other
   falls back to the parent's preceding siblings, so a `data class` constructor
   would inherit `data`.

`val` and `var` on a class parameter are deliberately not recorded. They make
the parameter a property declaration as well, which is a second consumer of the
same node and not a parameter fix.

### C++ default arguments (#315)

Dispatch tested `parameter_declaration` alone and skipped
`optional_parameter_declaration` entirely. So `void f(int a, int b = 2)`
reported ONE parameter, and nothing in the row said that one was missing.

The type needs a clamp and not a third cut. #283's rule keeps `int ` and ` = 2`
if it is applied unchanged, so the type would read `int = 2`. The window now
clamps to the start of the `=` token. Clamping also keeps everything to the left
of the `=`, so `int arr[3] = nullptr` reads `int[3]` rather than losing its
bound.

### One declarator walk, shared (#318)

`src/include/declarator_walk.hpp` holds #283's walk as a free function. The name
strategy and the native extractor both use it, so there is one implementation
and #283's and #315's tests keep covering it.

The walk is **additive, not a replacement.** It knows only C and C++ declarator
node types. Java's two `FIND_IN_DECLARATOR` sites do have a `declarator` field,
but it points at a `variable_declarator` whose name lives in a `name` field. The
walk returns null there, and the old search runs unchanged. Measured:
`languages/*` is 2245 assertions in 40 cases, identical, with
`java_refinements` and `c_refinements` both unmoved.

## A decision this release records but does not implement

**#186 — a root node is named by its path, literally.** Every language's root
node is unnamed, in all 27 of them. Teague chose the path exactly as given, over
a basename, NULL, or a dotted import path. His reason: a basename "will make
many files indistinguishable".

Measured before the question was put to him:

- The scope covers ALL 27 languages, not Python's `module` alone. The root node
  types are `program` (10), `source_file` (6), `document` (4),
  `translation_unit` (2), plus `chunk`, `stylesheet`, `config_file`,
  `compilation_unit` and `stream`.
- The current value is `''` on every one, and NULL on none. The issue's
  "`''` versus NULL" question is therefore settled by measurement.
- `scope.module` is an INT64 node reference, not a name, and it IS populated.
  109 of 110 rows in `simple.py` point at node 0, the module node. Only the name
  at the end of that link is empty.

**This does not land here.** 411 root rows in `test/data/**` would gain a name,
one per file parsed. That is content churn on every `read_ast` call in the suite.

## A claim this release had to correct about itself

**The performance section first published with this release was measured through
a harness that doubled every figure.** The DuckDB v2.0 CLI turns on agent mode
when `CLAUDECODE` is set, and agent mode plans every statement twice. On a query
whose cost is planning, that is a 100% tax. Every figure was therefore exactly
twice the real cost.

Four claims do not survive the correction, and the GitHub release body for this
tag still carries them:

1. **"75-87x", and "a further ~3x between dev86072 and dev88609".** Both came
   from doubled numbers. The real step from dev86072 to dev88609 is about
   +0.7 s.
2. **A DuckDB v1.5.6 row of `0.657 / 0.561 s`, read as a clean ~28x gap.** That
   row used the September extension against the November macro, so it never held
   the macro constant. It cannot be repaired cheaply either: the only v1.5.6
   binary in this repo predates current helpers and lacks
   `ast_semantic_aliases`. The comparison is withdrawn, not patched.
3. **"about 5.3 s" for this project's own macro growth.** That figure was
   derived from runs in separate sessions. Measured within one run, the
   September-to-November growth is about **4.5 s** (11.8 → 16.5 s).
4. **"because planning cost rises with statement size".** This is the wrong
   mechanism, and it is the most durable kind of error, because the number
   attached to it kept validating. About 12 s of planner time lived in the
   correlated subqueries of ONE pseudo-class `CASE`. A synthetic statement with
   32 correlated arms plans in 73 ms, so statement size alone never reproduced
   the cost. v1.18.4 decorrelates those arms and takes the call to about 2.9 s
   without shrinking the macro at all.

**The figures that do hold for this release** were measured with `-no-agent`
and `SET threads=1`, on DuckDB `v2.0.0-dev88609`. An `ast_select` call on
`simple.py` costs **18.230 s**. The equivalent plain query is 3-5 ms, so the
cost is planning. Detailed profiling of one call puts:

| phase | time |
|---|---|
| planner | 16.74 s of 18.49 s |
| binding | 0.047 s |
| the whole optimizer | 1.22 s |
| execution | 0.125 s of CPU |

`tracker/bugs/040` holds the corrected record. The wrong mechanism was also
published in `docs/briefs/2026-11-08-ast-select-performance.md`, which is now
marked RESOLVED.

## Known issues

### Filed by this release, and none of them a regression

- **#323** — Kotlin loses every class's parent types. The extractor looks for a
  `delegation_specifiers` child, PLURAL, which is absent from that grammar's 263
  node types. Java, from the same strategy, is correct.
- **#324** — a C++ function that returns a function pointer reports the RETURNED
  type's parameters as its own. #315 exposed it by giving `function_declarator`
  its parameters. Before that, a wrong answer sat behind a missing one.
- **#317**, **#320**, **#322** — C and C++ parameter type conventions differ,
  TypeScript drops a rest parameter, and no Zig parameter reaches the list.

### Carried from earlier releases

- **#276** and **#288** — `ast_definitions()` both duplicates a name that has a
  wrapper node, and misses a name bound by the bare-name hook. These are
  scheduled together.
- **#186** — every language's root node is unnamed. Decided, not implemented.
  See the decision section above.
- **`ast_select` is slow on DuckDB 2.0** (`tracker/bugs/040`). About 18 s per
  call at this tag, and the cost does not depend on the data. **Largely fixed in
  v1.18.4**, which takes it to about 2.9 s.
- **116 documented examples read an unbounded tree** (`tracker/bugs/055`).
- **Attribute filters inside `:has(...)` are not supported** (#150). The selector
  engine refuses them with a clear error.
- **`:precedes(type)` and `:follows(type)` accept a node type that does not
  exist** and return 0 rows rather than refusing.
- **`:exported` does not hold for Dart** (`tracker/bugs/056`).
- **The conformance kit runs nowhere in CI.**

## Upgrading

**Read "This release changes output" first.** This release is not drop-in for
every query.

The nine changes replace a wrong answer, or a missing answer, with a right one.
A query that read any of them was already reading a wrong answer. Three need
action:

- A query that counts C++ parameters sees larger numbers wherever a parameter
  has a default value.
- A query that reads a C++ parameter's `name` gets the parameter, not the type
  and not the default value. Where the parameter is abstract, the column is now
  empty.
- A query over C++ `DEFINITION_FUNCTION` rows now sees `parameters` filled on
  the `function_declarator` row as well as on the `function_definition` row. The
  two rows already shared the name and the return type, so a query that did not
  deduplicate was already getting two rows.

cause here. `spec/layout/layout.yaml` did not change at all, so the `DEF_TYPE`
move comes from the source tree.
