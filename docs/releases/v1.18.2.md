# Sitting Duck v1.18.2

**Release date:** 2026-11-06

A patch release of four selector-semantics defects. Three pseudo-classes
returned a wrong answer and gave no sign of it. The fourth looked like a filter,
discarded its argument, and answered with a plausible number; it now refuses.

**This release requires DuckDB 2.0**, unchanged from v1.18.1. The `duckdb`
submodule pin is still `d54cbbe3` (v2.0.0). No API changed shape.

## This release changes output

v1.18.1 changed no output value. This one changes five, which is the point of
it. Read this table before you upgrade.

| Selector or option | Before | After |
|---|---|---|
| `.fn:calls(.fn#execute)`, `:calls()`, `:called-by(.fn#main)` | a number | an error |
| `.func:not(:is-referenced)` | always 0 rows | the unreferenced definitions |
| `.var:in-scope(.class#customers)` on SQL | 0 rows | 4 rows |
| `read_ast()` `flags`: `IS_EXPORTED` on a function inside a function body | set | not set |
| `read_ast(..., prune := ['internal'])` on `edge_cases.py` | 11 functions | 8 functions |

**The `IS_EXPORTED` change reaches beyond `ast_select`.** The flag is part of
`read_ast()` output, so any query that calls `is_exported(flags)` sees it, and
`prune := ['internal']` prunes on it. Nothing else in the flag set moves.

## Behaviour change

### `:calls()` and `:called-by()` refuse a non-name argument (#191)

These two pseudo-classes take a bare function name. Every other argument shape
was parsed, discarded, and then treated as "no filter given". The pseudo-class
matched every node with any call, and the caller got a plausible, non-empty
number back.

Measured before the fix, on `test/data/python/sample_app.py`, where `.fn` is 20:

```
.fn:calls(execute)          4   correct
.fn:calls(.fn#execute)     17   argument ignored
.fn:calls(#execute)        17   argument ignored
.fn:calls(*)               17   argument ignored
.fn:calls()                17   no argument at all
.call:called-by(.fn#main)  44   argument ignored
```

17 is "functions that call anything". 44 is "calls inside any function". Each
of those shapes now raises:

```
ast_select: :calls() takes a function NAME, for example :calls(execute). The
argument given is not a name. It would be ignored, and the filter would then
match every node with any call. Selector arguments (#name, .class, .class#name)
are not supported here. To match regardless of name, write the pseudo-class
bare, with no parentheses.
```

**The bare form is untouched.** `.call:called-by`, with no parentheses, is a
different and deliberate predicate: "this node has some enclosing function". So
is bare `:calls`: "this function calls something". The guard fires only when an
argument block was written and yielded no name.

**Why an error rather than the feature.** A later release will teach `:calls()`
to accept a selector argument, and will add `:calls-name()` as the explicit
scalar spelling. A bare name can never begin with `.` or `#`, so the two shapes
cannot collide. Until that exists, these selectors must not be answered with a
number that looks like a filter. The error is the bugfix, and it becomes that
feature's dispatch point.

The naming follows CSS and Playwright. Both reserve the plain functional
pseudo-class for selector arguments (`:has`, `:not`, `:is`, `:where`) and
qualify the scalar variant (`:lang`, `:dir`, `:has-text`). It also follows this
dialect's own rule, where a bare token is a node type, `.x` is a semantic class
and `#x` is a name — which makes `:calls(execute)` the only place in the
language where a bare token means a name.

## Fixes

### `:is-referenced` counted a definition's own name (#147)

A definition's name is a separate node, a direct child of the definition, and it
carries `NAME_REFERENCE`. Measured on `sample_app.py`:

```
node_id  type                 name       is_def  is_ref  parent_id
761      function_definition  transform  true    false   --
763      identifier           transform  false   true    761
```

The predicate looked for any `NAME_REFERENCE` node with the same name and a
different `node_id`, so node 763 answered for node 761. Every named definition
matched `:is-referenced`, and `.func:not(:is-referenced)` — which the reference
presents as *the* dead-code query — returned 0 rows always.

The rule now is: a reference inside the definition's own subtree does not count.
That excludes a recursive self-call, deliberately. The documented purpose is
dead-code detection, and a function called only by itself is dead.

`ast_dead_code()` is unchanged and may disagree about a self-recursive function.
It matches on name alone, counts every call name including a self-call, and
excludes `main`, `setup`, `teardown`, `init`, `constructor` and dunder names
outright. These are different questions, not two answers to one question.

### `:in-scope(.class#X)` returned nothing where the class is not a scope provider (#166)

The `.class` branch read the precomputed scope struct, which the traversal fills
only under nodes flagged `IS_SCOPE`. A semantic class need not be a scope
provider. Measured on `test/data/sql/example.sql`:

```
.class#customers                          1
.var:in-scope(.class#customers)           0   <- silently empty
.var:in-scope(create_table)               4
create_table#customers column_definition  4   <- the right answer
```

SQL's `create_table` is `DEFINITION_CLASS` with `is_scope = false`, so
`scope.class` is NULL on every node beneath it and the branch could never hold.
The bare-type form answered 4 on the same file, so the two argument forms
disagreed.

The branch is now a `CASE`. The struct fast path is unchanged and still runs
wherever `scope.class` is set, so no language with real scope providers moves.
The fallback walks ancestors by descendant range, restricted to class
definitions, and keeps the nearest-enclosing rule.

**Not fixed, and deliberately not fixed blind:** the `function` and `module`
branches have the same structural hole. A language whose functions are not scope
providers would fail the same way. No fixture in this repo shows it, so there is
nothing to measure and nothing is changed there.

### `:exported` matched definitions inside a function body (#148)

`IS_EXPORTED` is set in one place, gated on the per-language visibility rule. It
now also requires that the node is not inside a function body. A function
defined inside another function's body cannot be imported, whatever its name.

A method is deliberately still matched. Its nearest scope is a class, and the
class is reachable from outside.

**This is not the fix #148 asked for.** The issue reports that `:exported`
wrongly "includes methods and nested functions, while the docs define it as
module-level public definitions". The docs sentence was the defect. Several
languages treat a public method as public API, so a module-scope rule would
empty the pseudo-class of meaning in them — Java would match only top-level
public types. For the module-level subset, `ast_exports()` already exists and
does not move: `is_exported(flags) AND COALESCE(scope.current, 0) = 0`.

`prune := ['internal']` narrows with the flag. Measured on
`test/data/callgraph/edge_cases.py`: 11 `function_definition` nodes become 8,
losing exactly the three nested ones and keeping both methods. That policy had
no test of its own before this release; it has two now.

**`ShouldPruneNode` had to change with it, and this was caught in review, not
by a test.** The first version of this work left the policy pruning *any*
name-binding node without `IS_EXPORTED`. Since the flag is now strict, that
included every parameter and local inside a function body, so the policy
deleted the bodies of the functions it keeps. Measured on
`test/data/python/sample_app.py`: 1246 nodes became 841, `assignment` 26 became
2, `call` 45 became 30. 73 nodes lost the flag and only 3 were the nested
functions #148 is about.

The predicate is now:

    BINDS_NAME && !IS_EXPORTED && (importable_kind || !inside_function)

where `importable_kind` is semantic base `DEFINITION_FUNCTION` or
`DEFINITION_CLASS`. Inside a function body only functions and classes are
pruned; locals, parameters and destructuring targets are kept. So the policy
gives the public API surface with its implementations intact. On
`sample_app.py` that is 1158 nodes, `assignment` 20, `call` 45, and
`edge_cases.py` still gives 8 functions with the same names.

## Documentation

**The reference now states three rules a caller can rely on**, each with the
issue that settled it: the `:calls` / `:called-by` argument rule, the
`:is-referenced` self-reference rule, and the `:in-scope` scope-provider rule.

**The bare, parenthesis-free `:calls` and `:called-by` are documented for the
first time.** The reference listed only `:calls(name)`. The suite has asserted
the bare form deliberately since before this work, in three files. A form that
the tests depend on and the documentation omits is invisible to a reader and to
a search.

## A claim this release had to correct about itself

The commit messages for #148 state that five languages implement visibility, and
that "in Go, Java, JavaScript and C++ a public method IS public API". Both parts
are wrong, and the second is wrong in the direction that matters.

Measured: **28 per-language adapters implement `IsPublicNode`**, not five. And
`JavaScriptAdapter::IsPublicNode` tests the node's own type and its parent's
type for `export`. A method's parent is `class_body`, so the function can never
return true for a method.

Measured by running it, on an `export class` holding one method:

```
js  class_declaration    Service        exported
js  method_definition    publicMethod   NOT exported
js  function_declaration topLevel       exported
ts  method_definition    publicMethod   exported       -- `public` is written
ts  method_definition    bareMethod     NOT exported
py  function_definition  public_method  exported
```

So TypeScript matches a method only where `public` is written, and JavaScript
matches none. C#, Java and Rust return false unless the declaration says
otherwise.

The reasoning behind the fix survives the correction, because C++, Python, Go,
Ruby and Dart do treat a public method as public API. The count did not survive.
`docs/reference/css-pseudo-classes.md` now carries eleven measured rules, says
that 28 adapters have one, and states the JavaScript and TypeScript exceptions
with the measurement above.

## Known issues

Unchanged from v1.18.1 except where noted, and none of them is addressed here.

- **`ast_select` is slow on DuckDB 2.0** (`tracker/bugs/040`). Planning is
  single-threaded and dominates: each `ast_select` call measured about 37 s on a
  36-core box on 2026-11-05, and the cost does not depend on the data. The cause
  is upstream, [`duckdb/duckdb#26036`](https://github.com/duckdb/duckdb/issues/26036).
- **116 documented examples read an unbounded tree** (`tracker/bugs/055`).
- **Call-graph pseudo-classes can exhaust memory** (#164). This may already be
  retired by the `:called-by` equi-join rewrite. It is not re-measured here.
- **Attribute filters inside `:has(...)` are not supported** (#150). The
  selector engine refuses them with a clear error.
- **`:precedes(type)` and `:follows(type)` accept a node type that does not
  exist** and return 0 rows rather than refusing. Found while fixing #191, not
  fixed here.
- **The conformance kit runs nowhere in CI.**

## Upgrading

**Read the output-change table at the top of this page first.** This release is
not drop-in for every query, which v1.18.1 was.

Three of the five changes replace a wrong answer with a right one, so a query
that was reading them was already reading a wrong answer. Two need action:

- A selector of the form `:calls(.fn#x)`, `:calls(#x)`, `:calls(*)`, `:calls()`
  or `:called-by(<anything but a name>)` now raises. If the intent was "matches
  any call", write the pseudo-class bare, with no parentheses. If the intent was
  a name filter, write the bare name: `:calls(execute)`.
- A query that reads `is_exported(flags)` sees the flag cleared on **every**
  definition inside a function body, locals and parameters included, not only
  on nested functions. For the module-level subset, use `ast_exports()`.
- `prune := ['internal']` drops nested functions and classes, and keeps locals
  and parameters, so the bodies of the functions it keeps survive. If you
  depended on it dropping private module-level variables, that is unchanged.

**`:exported` does not hold for Dart.** Dart's `function_signature` carries
the name and is a sibling of its `function_body`, not its parent, so a Dart
function body is not recognised as being inside a function. A Dart local still
matches `:exported` where the same Python shape does not. This equals the
behaviour of every earlier release, so it is an incompleteness and not a
change. Covering it needs each of the 28 adapters to say which node opens a
function body, which is not a bugfix-release change. Recorded in
`tracker/bugs/056`, and pinned as current behaviour in
`test/sql/bugs/148_prune_internal_body_and_config.test` section 6.

## Verification

Measured on the release candidate, not carried over from earlier runs.

**Full suite, measured on the release binary.** 178 test files, no failure:

```
All tests passed (5 skipped tests, 9210 assertions in 173 test cases)
```

The 5 skipped files need `SITTING_DUCK_TEST_GRAMMAR_DIR`, which this run does
not set. The denominator moved from 177 files to 178, which is the one new test
file in this release.

The count was predicted before the run ended, and the prediction holds. 9210 =
9122 from the earlier full run, plus 88 for the five changed or new files
(14 + 26 + 8 + 10 + 30). An assertion count is per query, not per row, so a
move in an untouched file would have been a failure, not arithmetic.

`make test_release` runs the unittest binary directly, with no test runner, so
the total prints once, at the end. A run that stops early gives no count at
all. The first candidate run met its 9000-second budget at file 114 of 177, and
therefore measured nothing.

The same run measured why the suite is long. Two files need 90 minutes
together: `ast_select_pseudo_classes.test` at 2709.8s and
`css_selectors_multilang.test` at 2654.9s. The four slowest total 6960s. The
`Makefile` already records about 7500s for those four files, and names
`duckdb#26036` as the cause. The measurement agrees with that record, so this
release does not add to the cost.

- **The five new test files, run on their own:** 14 assertions (#147), 26
  (`148_exported_scope`), 8 (#166), 10 (#191), and 30
  (`148_prune_internal_body_and_config`, the review rework). 88 together, which
  is the increment in the full-suite total.
- **The three existing files that the #191 guard could have broken, run on
  their own against the release binary:** 18 assertions
  (`issue_146_calls_scope_edge_cases`), 196 (`scope_resolution/callgraph_macros`),
  104 (`ast_select_pseudo_classes`). All three assert the bare, argument-free
  form of `:calls` and `:called-by`, which the first version of the guard
  refused. They are the control for that error.

- **The #191 test is a stale-binary control in both directions.** Against a
  binary built before the guard, its four `statement error` blocks fail, because
  the query succeeds and returns a number. Against a binary carrying the first,
  too-broad version of the guard, section 3 fails instead, because the bare form
  raises. So its 10 passing assertions are positive evidence that the tested
  binary carries this exact guard, not merely that nothing failed.
- Module ABI gate: `OK`, 17 strategies (11 dispatched, 6 reserved), 20 traits
  mappings over 28 per-language adapters, 330 non-NONE declarations in 28
  languages, 85 `(language, strategy)` pairs.
- Native dispatch gate: `OK`, **69 known-dead literals of 1380** across 27
  languages, exactly as `spec/abi/module-abi.yaml` records them, and no new
  ones.
- `DEF_TYPE` table gate: `OK`, 3837 entries across 31 translation-unit roots,
  every entry closing on its own line, no raw type declared twice in one
  translation unit.
- Layout invariance gate: `OK`, 28 language modules each resolving at the
  spec's paths, 4039 `DEF_TYPE` entries across 58 files.

All four gates report the same figures as v1.18.1. That is the expected result
rather than a reassuring one. `src/` changed in three files — the selector
macros, the header generated from them, and the one line that sets
`IS_EXPORTED` — so a moved figure would have meant something unintended had
changed.

**No new formatting violation.** `make format-check` fails on `main` and on this
release for the same 17 files, which include `CMakeLists.txt`, the generated
`src/include/embedded_sql_macros.hpp` and four `.test` files. For the two files
this release edits, the reported violation text is byte-identical between `main`
and the release commit. `make format-fix` is not run here, because it would
rewrite 15 files this work never touched.

What is **not** re-measured: the conformance kit's full matrix, which took
52m38s for v1.18.0 and which no selector-macro change can reach; and the
planning-cost figures in the #147 and #166 commit messages, which were taken on
a shared box under foreign load and are recorded there as unseparated from
run-to-run spread.
