# v1.18.3 — names that do not bind, or bind to the wrong thing

**Status:** Approved and in progress. Done: #273, #277, #140a, #140b, #140c,
#283, #263. Remaining: #315, then **#318**, then #288 with #276, then #186.
**Drafted:** 2026-11-06. **Last amended:** 2026-11-07, when #315 was planned.
**#318 admitted** on 2026-11-07: Teague answered "318 is ok" to the stated
default, so `FIND_IN_DECLARATOR` is fixed in place in this release, after #315.
#317 collapses into that fix.
**Scope decision:** names in v1.18.3, type misclassification in v1.18.4.
`#223`, `#255` and `#136` are deferred as features; `#260` is a breaking return-type
change and belongs to v1.19.0.

## Why these nine issues are one release

Nine open issues share one symptom: a name that a user can see in the source does
not come back from `ast_definitions()`, or comes back wrong. They do **not** share
one cause. Measured on Go at `55100c5`, there are three distinct shapes, and a
single fix closes only one of them.

| Shape | Example | `name` carried by | NAME_ROLE | `semantic_type` | in `ast_definitions()` |
|---|---|---|---|---|---|
| works | `var y int = 2` | `var_spec` | DEFINITION | `DEFINITION_VARIABLE` | yes |
| **A — invisible to the macro** (#288) | Python `for zz in items` | `identifier` | DEFINITION | `NAME_IDENTIFIER` | no |
| **B — nothing bound it** (#277) | Go `x := 1` | `identifier` | none | `NAME_IDENTIFIER` | no |
| **C — wrapper is not a definition** (#140) | Go `type Point struct` | `type_spec` | none | `EXECUTION_DECLARATION` | no |

Shape A is a macro predicate. Shape B is a missing extraction. Shape C is a
misclassified node. In shape C the inner `type_identifier Point` reads
`TYPE_REFERENCE`, so Go's struct name is currently a *reference to itself*.

A fourth shape is worse than all three, because it answers rather than omits:

| Shape | Example | `name` | correct |
|---|---|---|---|
| **D — wrong name** (#273) | `self.db = conn` | `conn` (the right-hand side) | no |

#273's own words: "A wrong definition is worse than a missing one: a
scope-resolution query gets a false binder rather than no answer."

## The sequencing constraint that drives the plan

**#288 and #276 pull in opposite directions on the same output.**

- #288: hook-bound names are **absent** from `ast_definitions()`, so the fix
  **adds** rows.
- #276: container and declarator nodes both carry NAME_DEFINITION, so
  `ast_definitions()` already returns a name **two or three times**; the fix
  **removes** rows.

Fixing #288 alone multiplies the duplicates #276 reports. Fixing #276 alone
hides how many names #288 would add. Both change every count any test asserts
over `ast_definitions()`. So they are one coordinated change with one
test-accounting pass, and they go **last**, after the per-adapter bindings have
stopped moving.

The per-adapter fixes do not need #288 first. #277's fix puts a name on
`short_var_declaration`, which already carries `DEFINITION_VARIABLE`, so it
becomes visible immediately.

## Order of work

Each numbered item is a test commit verified red, then an implementation commit.
The Golden Rule holds throughout: implementation or tests, never both at once.

**0. Survey, no code.** Re-measure all nine against the current build and record
current-versus-expected per binding site. #64 is the checklist for this step, not
a deliverable — see "Two decisions" below.

**1. #273 — the wrong name.** Independent of the macro. An `assignment` whose
target is not a bare identifier must stop reporting the right-hand side as a
definition. Python and Ruby both show it. The honest fix may be to bind nothing
where the target is not a name, which turns shape D into shape B — a smaller
defect, and one already covered by this release's other work.

**2. Per-adapter extraction, one commit pair each.** These are isolated and
independently verifiable:
  - **#277** Go `short_var_declaration`. `FIND_IDENTIFIER` returns the first
    `identifier` child, but tree-sitter-go puts `left` in an `expression_list`,
    so it finds nothing. Needs a strategy that descends the list — and `a, b := 1, 2`
    binds two names, which `name` (a single column) cannot hold. That case must
    be stated, not silently half-fixed.
  - **#140a** Bash command words. 22 of 95 `command` nodes are named.
  - **#140b** Go `struct_type` / `interface_type` names on `type_spec`.
  - **#140c** Java import names are the whole statement text, including
    `import ` and the semicolon. Python already returns clean module paths, so
    Python is the reference shape.
  - **#283** C++ variadic parameters: the three qualified forms
    (`const Args&...`, `Args&&...`, `Args*...`). The pointered form produces no
    `function_definition` row at all, which is the most serious of the three.
  - **#263** Kotlin `primary_constructor` declares native strategy `NONE`. This
    is a declared gap, so the conformance kit passes it correctly. Changing it
    means changing the declaration and the extractor together, and the kit's
    `NATIVE-DECL` line for Kotlin will move from 2/6 to 6/6.
    **Corrected 2026-11-07:** the 6/6 figure is unverified — the kit runs nowhere
    in CI and I have not run it. The claim that the mirror files move with it is
    wrong; they pin the language *set*, not per-node counts. See "The #263 plan"
    below for the blast radius stated per pin.
  - **#315** C++ default arguments. **Added to the release on 2026-11-07**, after
    it was found while landing #283 — see "The tenth fix" below.

**3. #288 + #276 together.** One test-accounting pass over everything that
asserts `ast_definitions()` counts. The change is in

**4. #186 — module names.** Blocked on a naming decision, below.

## Two decisions needed

**#64's fate.** It is an audit across 27 `.def` files, not a defect. Its
"likely missing" list is now covered by specific issues: bare parameters by
#288, for-loop targets by #288, Go declarations by #277, `variable_declarator`
by #276, field declarations by #276. Either it becomes step 0's checklist and is
closed as superseded, or it stays open as a standing audit. It should not be
counted as a tenth fix. **The tenth fix turned out to be #315**, found by
measuring rather than by auditing — which is the argument for step 0 being a
measurement pass and not a document review.

**What a module's name is.** #186 reports every `module` node with `name = ''`
— 19 of 19 in `test/data/python/*.py`, consistently empty and never NULL. So
`:is-scope(module#x)` parses, runs, and can never match. The issue itself leaves
the choice open: the basename without extension (`unicode` for `unicode.py`), or
the dotted import path where a project root can be derived (`pkg.sub.unicode`).
The basename is local and always available; the dotted path needs a root and is
wrong when there is none. This needs a deliberate answer, because it is the
value that every module-scope query will match on afterwards.

## The tenth fix: #315, admitted on 2026-11-07

Found while measuring #283, not by reading the issue list. A C++ function with a
default argument drops **every defaulted parameter** from its `parameters` list,
so the arity is short but plausible:

| source | reports | actual |
|---|---|---|
| `void m1(int a, int b = 2)` | 1 | 2 |
| `void m2(int a, int b, int c = 3)` | 2 | 3 |
| `void m3(const std::string& s, bool flag = true, int n = 0)` | 1 | 3 |

That is shape D's failure mode, not shape B's: it answers rather than omits, and
#273's own words apply — "a wrong definition is worse than a missing one". A
caller cannot tell a short list from a complete one.

**Why v1.18.3 and not v1.19.0.** Teague's instruction was to admit it unless it
belonged to v1.19.0. It does not, on four measured grounds:

1. It is this release's own subject. The cause is a dispatch arm naming
   `default_parameter_declaration`, which no grammar emits, while the real node
   is `optional_parameter_declaration` (`grammar.js:455`). That is the #220
   shape for the fourth time in this release's lineage.
2. `languages/cpp/cpp_types.def:196` already declares the node and the AST row
   already carries the name, so there is **no `.def` change** — none of the
   three CI gate classes in the survey is engaged.
3. The fix is one dispatch arm plus excising the `default_value` field in the
   helper #283 added, in the same function. No schema change, no taxonomy move,
   no breaking return type.
4. It needs **nothing from #255**. `is_optional` and `default_value` are set and
   stay invisible to SQL, exactly as `is_variadic` does after #283. Were the
   schema change required, v1.19.0 would have been right.

**Where it goes in the order:** after #263 and before #288+#276. It is
independent of #263 — different language, different file — so the order between
those two is free, and #263 keeps its approved slot. It must come before step 3,
because adding parameters moves counts and step 3 is the test-accounting pass.

**Its blast radius is real but narrow.** 67 `optional_parameter_declaration`
nodes across 15 files in our own tree, so any pin asserting a C++ parameter
count over one of those files moves. That is the same shape as #283's blast
radius and smaller, because it moves counts rather than strings.

Two siblings were filed at the same time and are **not** in this release:
**#316** (C++ lambdas report zero parameters, cause not established) and
**#317** (C and C++ return different parameter types for identical source).
Neither is a name-binding defect, and #317 wants a shared-helper decision across
two adapters.

## Risks

- **Test-count churn.** Step 3 moves counts in any file asserting
  `ast_definitions()`. Several fixtures glob `test/data/**`, so adding a probe
  file also moves unrelated counts — bug 055's unbounded-glob problem. New
  fixtures go outside the globbed trees, as `test/data/callgraph/` already does.
- **A fix that only half-lands.** #288's own report shows this already happened:
  #274 and #279 are closed but "half-closed in practice", because a role flag
  reaches scope resolution and not the macro most queries use. Every item here
  needs its assertion written against `ast_definitions()`, not only against
  `is_name_definition(flags)`.
- **One name column, two names.** Go `a, b := 1, 2` and JS `let a = 1, b = 2`
  both bind two names on one container. #276 calls the JS case "the sharpest":
  the container claims the single name `a`. No single-valued `name` column can
  be right here, so the plan must say what it does instead of picking one.
- **Suite cost.** A full local run is about 2.4 hours and prints its only count
  at the end. CI's coverage leg runs the same 173 cases in about 27 minutes, so
  CI is the cheaper gate for a count.

## The #263 plan, measured 2026-11-07 — approved, and landed

Step 2's remaining item. Everything below is **measured** against the binary
built from `89d7816`, not read from the issue.

### The shape, which is not the shape the existing walk handles

`primary_constructor`'s items are `class_parameter` nodes as **direct
children**. There is no `function_value_parameters` container:

```
class Person(val name: String, var age: Int = 0)

class_declaration                 name = Person
  type_identifier                 Person
  primary_constructor             name = <empty>   <- the gap
    "("
    class_parameter               name = name      <- row already correct
      binding_pattern_kind > val
      simple_identifier           name
      ":"
      user_type > type_identifier String
    ","
    class_parameter               name = age
      ...
      "="                         <- default is a CHILD of class_parameter,
      integer_literal  0             not a sibling of it
    ")"
```

`secondary_constructor` is a **different** shape with the **same** declared gap:
`constructor`, then `function_value_parameters` holding `parameter` children with
the default as a sibling. That is exactly what `ExtractKotlinParametersDirect`
already handles.

So the two constructors need two branches, and only one of them needs new
walking code.

### Three traps in the obvious reuse, each one measured

**1. The dispatch is already fine, and that is what makes it dangerous.**
`ExtractNativeContextTemplated` (`native_context_extraction.hpp:512`) is generic
over the adapter, it has a `CONSTRUCTOR_DEFINITION` case at `:540`, and
`KotlinAdapter` has a traits specialization at `:447`. But
`KotlinNativeExtractor<CONSTRUCTOR_DEFINITION>` **does not exist**, so changing
only the `.def` would fall through to the base template at
`kotlin_native_extractors.hpp:17` and return an empty `NativeContext`. That is
the #220 shape: declared, dispatched, and silently empty. The specialization is
mandatory; no dispatch change is needed.

**2. `ExtractKotlinParameter` must not be reused as it stands.** Measured on
`class P(val x: Int = y)`, a `class_parameter` has **two** `simple_identifier`
children — the name `x` and the default `y` — and the loop at
`kotlin_native_extractors.hpp:172` assigns `param.name` on every match and never
breaks. It would report the parameter's name as **`y`**.

That is this release's own defect class for the seventh time: *the name is
nested, and a plausible wrong candidate sits next to it — here the default
value.* It is also why the fix cannot be a delegation. The walk must stop taking
name and type at the `=` child, and read the default from the node after it. The
existing `default_value` branch at `:191` is dead: tree-sitter-kotlin emits no
such node.

**3. `FUNCTION_WITH_PARAMS::Extract` must not be delegated to either.** Two
reasons, both in code already read:

- `ExtractKotlinReturnType` falls through to `return "Unit"`. A constructor has
  no return type. Java's `CONSTRUCTOR_DEFINITION` sets `signature_type = ""`
  deliberately (`java_native_extractors.hpp:1012`), and that is the precedent to
  follow.
- `ExtractKotlinModifiers` has a parent-sibling fallback at `:244` whose accept
  list includes `class_modifier`. Measured on `data class Person(val name:
  String)`: `modifiers` is a **preceding sibling** of `primary_constructor` under
  `class_declaration`, so the constructor would inherit `data`. The same holds
  for `sealed` at `simple.kt:62`.

So the specialization builds its context directly: parameters from the
`class_parameter` walk, `signature_type = ""`, and modifiers from the
constructor's own `modifiers` child only. A control asserts that the `data
class` constructor does **not** carry `data`.

### Scope: secondary_constructor, as a vetoable default

`secondary_constructor` (`kotlin_types.def:92`) carries the identical `NONE` /

**Default: include it.** It is the same defect in the same node family and the

### The decision this plan cannot make: what the constructor is named

`primary_constructor` also declares name strategy `NONE`, so these constructors
are unnamed and `.fn#Person` reaches nothing. The house has **two** conventions,
measured, and they conflict here:

| language | constructor name | where it comes from |
|---|---|---|
| java | `P` | an `identifier` child, via `FIND_IDENTIFIER` |
| cpp | `P` | same shape |
| csharp | `P` | same shape |
| swift | `init` | the keyword, via `CUSTOM` |
| python | `__init__` | the method's own name |

Kotlin's primary constructor has **neither** an identifier child nor a
`constructor` keyword — `class Person(val name: String)` contains no token that
names it. So "the class name" needs a parent lookup that no existing name
strategy performs, and "the keyword" would be a literal with no source backing.

This is kept **out of #263's commits** on purpose: it is a convention choice, it
would move `ast_definitions()` rows, and step 3 is where count churn belongs.

## #315 plan — C++ default arguments, measured before written

**Drafted 2026-11-07, awaiting approval.** Every number below is measured
against `build/release` as built at `3e41f6e`, through
`parse_ast(..., 'cpp')`, or read out of
`grammars/tree-sitter-cpp/src/node-types.json` and `grammar.js`.

### What is wrong, measured

```
void f(int a, int b = 2, const char* s = "x") {}
  function_definition f  parameters = [{'name': a, 'type': int}]
```

Arity is **1** where the source has **3**. The two defaulted parameters are not
reported with a missing default; they are not reported at all. `read_ast` says
nothing about the gap, so the short list reads as a complete one.

`ExtractCppParametersDirect`
(`src/include/cpp_native_extractors.hpp:618-635`) dispatches on two node names:

```cpp
if (strcmp(child_type, "parameter_declaration") == 0) { ... }
else if (strcmp(child_type, "variadic_parameter_declaration") == 0) { ... }
```

`grammar.js:456` names a defaulted parameter `optional_parameter_declaration`,
which is neither, so the child is skipped and never pushed.

### The grammar, read not guessed

```js
optional_parameter_declaration: $ => seq(
  $._declaration_specifiers,
  field('declarator', optional(choice($._declarator, $.abstract_reference_declarator))),
  '=',
  field('default_value', $.expression),
),
```

Three measured facts come out of that rule and out of a parse:

1. `default_value` is a **field**, so it needs no scan.
2. `declarator` is **optional** — `void h(int = 2)` is a legal parameter with no
   name, and it parses as an `optional_parameter_declaration` with no declarator.
3. The `=` is a **direct anonymous child**, between the declarator and the
   default value. Measured on `void f(int arr[3] = nullptr, const std::string& s = "x")`:
   children are `primitive_type`, `array_declarator`, `=`, `null`; then
   `type_qualifier`, `qualified_identifier`, `reference_declarator`, `=`,
   `string_literal`.

### The fix: one arm, one helper, one cut

**1. The dispatch arm** in `ExtractCppParametersDirect`, beside the two that are
already there.

**2. A new `ExtractOptionalParameterDeclaration`** that reuses both of #283's
helpers rather than adding a third rule for names or types
(ponytail rung 2 — it is already in this codebase):

```cpp
TSNode declarator = ts_node_child_by_field_name(node, "declarator", 10);
TSNode name_id = FindDeclaratorId(declarator);      // null for `void h(int = 2)`
param.name = NodeText(name_id, content);
param.type = DeclaredTypeText(node, name_id, content);
TSNode default_value = ts_node_child_by_field_name(node, "default_value", 13);
if (!ts_node_is_null(default_value)) {
    param.default_value = NodeText(default_value, content);
    param.is_optional = true;
}
```

`is_optional` and `default_value` are invisible to SQL, exactly as
`is_variadic` is. So they are recorded because `ParameterInfo` has the fields,
not because a test can see them — and the test says so, rather than pretending
to cover them. This is why #315 does **not** need #255.

**The annotations loop is deliberately left out.** `ExtractParameterDeclaration`
copies `storage_class_specifier` and `type_qualifier` into `annotations`, which
is also invisible to SQL. `ExtractCppVariadicParameterDeclaration`, #283's own
sibling helper, does not. The nearest house precedent is therefore to omit it,
and omitting it keeps the change to what the issue asks for.

**3. The type cut.** `DeclaredTypeText` builds a type by excising byte ranges
from the declaration: the specifiers that are not part of the type, and the
name. Applied unchanged to `int b = 2` it keeps `int ` and ` = 2`, so the type
would read **`int = 2`**. The default has to be excised too.

The cut runs **from the `=` token to the end of the declaration**, not from the
default value's own start, because starting at the value would leave `int =`.
It does not run from the end of the name either, because
`int arr[3] = nullptr` must keep its array bound: cutting name and tail gives
`int [3]`, and `NormalizeDeclaredType` already closes that gap to `int[3]`,
which is the convention #283 documented.

It is not a third cut. `DeclaredTypeText` already works inside the window
`[decl_start, decl_end)`, so the window itself is **clamped**: at the top of the
function, `decl_end` becomes the start byte of the `=` token, which is
`ts_node_prev_sibling` of the `default_value` field.

```cpp
TSNode default_value = ts_node_child_by_field_name(decl, "default_value", 13);
if (!ts_node_is_null(default_value)) {
    TSNode eq = ts_node_prev_sibling(default_value);   // the `=` token
    if (!ts_node_is_null(eq)) {
        decl_end = ts_node_start_byte(eq);
    }
}
```

A third cut was the first design and it is worse two ways. It has an **ordering
trap**: the specifier cuts are pushed during the child loop and the name cut
after it, so a tail cut pushed inside the loop would sit before the name cut,
break the vector's source order, and the apply loop — which skips any cut
starting behind the cursor — would then leave the name in the type. It also
leaves a corner open: for `void h(int = 2)` there is no name, so `name_start`
falls back to `decl_end`, and the specifier guard `child_end <= name_start`
would then admit a `comment` child sitting after the `=`. Clamping the window
makes both impossible, because nothing after the `=` is in range to begin with.

The clamp is a no-op for the two node types that call `DeclaredTypeText`
today: `node-types.json` gives neither `parameter_declaration` nor
`variadic_parameter_declaration` a `default_value` field, so the lookup returns
null and the window is unchanged. The four forms `int`, `int[3]`,
`const std::string&` and `const int&` will be **measured** through the existing

## #318 plan — one declarator walk, measured before written

**Drafted and APPROVED 2026-11-08.** Measured against `build/release` at
`6486820`. Asked where to wire the walk, Teague chose **"Fix
FIND_IN_DECLARATOR in place"** over a C++-only strategy enumerator and over
also making java field-precise. So the plan below stands as written: one walk,
one definition, C's `fp_ret` name fixed as a side effect and pinned, java
unchanged by falling back.

### The defect, and the one that sits beside it

| source | `name` today | should be | what it returned |
|---|---|---|---|
| `int b` | `b` | ✓ | |
| `const std::string& s` | `std::string` | `s` | the **type** |
| `int* p` | *(empty)* | `p` | |
| `int& r` | *(empty)* | `r` | |
| `int& r = global` | `global` | `r` | the **default value** |
| `int = x` | `x` | *(empty)* | the **default value**, where there is no name at all |

`FindIdentifierInChildren` (`src/language_adapter.cpp:297`) tries a fixed list
of DIRECT child types in order — `identifier`, `property_identifier`,
`field_identifier`, `qualified_identifier`, `name`, … — so when the real name
is nested inside a `reference_declarator` or `pointer_declarator` it lands on
whichever listed type happens to be a direct child: the type, or the default
value.

**Measured beside it, and not in the issue:** `FIND_IN_DECLARATOR` is itself
defective for the same reason.

```
int* f(int a)                      (c)  name = f        correct
int (*fp_ret(int a))(char)         (c)  name = int      WRONG -- the return type
class K { int[] arr = null; }    (java) name = arr      correct
void m() { int[] a = null; }     (java) name = a        correct
```

So the two strategies fail on the same shape, and C's `function_definition`
name is wrong for a function returning a function pointer.

### Why one shared walk, and why it cannot simply replace FIND_IN_DECLARATOR

`FindDeclaratorId` (`cpp_native_extractors.hpp:77`) already performs the exact
walk both need, and the grammar bounds it exactly: `pointer_declarator`,
`array_declarator`, `function_declarator` and `init_declarator` each carry a
`declarator` FIELD, and a `function_declarator`'s own parameter list is a
SEPARATE `parameters` field, so the walk can never descend into a function
pointer's parameters and mistake one for the name. It carries 44 + 74 passing
assertions behind it.

**But it is C/C++-shaped.** Measured from `tree-sitter-java`'s
`node-types.json`, java's two `FIND_IN_DECLARATOR` sites do have a
`declarator` field — pointing at a `variable_declarator`, whose name lives in a
**`name`** field, not a `declarator` field. The walk would reach
`variable_declarator`, find no case for it, and stop. So java must keep its
present behaviour, and the walk must be ADDITIVE rather than a replacement.

### Four edits

| # | Edit |
|---|---|
| 1 | New `src/include/declarator_walk.hpp`: the walk as a free function, plus the list of node types whose name IS the declarator-id |
| 2 | `cpp_native_extractors.hpp`'s `FindDeclaratorId` forwards to it, so there is one definition and #283's and #315's tests keep covering it |
| 3 | `LanguageAdapter::ExtractNameFromDeclarator` tries the walk FIRST and falls back to its existing type-pattern search |
| 4 | `languages/cpp/cpp_types.def:191` and `:196`: name strategy `FIND_IDENTIFIER` -> `FIND_IN_DECLARATOR` |

**Layering.** `src/language_adapter.cpp` includes only adapter-level headers,
and `cpp_native_extractors.hpp` is included by exactly one file,
`native_context_extraction.hpp`. So the walk cannot live where it is now; it
needs a neutral header both layers may include. That is the only structural
reason edit 1 exists.

**The trap in edit 3, found before writing it.** A plain fall-back would leave
`int = x` reporting `x`: the walk returns null because there is no declarator,
and the old search then finds the default value's `identifier`. For a parameter
node an ABSENT declarator means there is no name, so the fallback must be
suppressed for those node types — `parameter_declaration`,
`optional_parameter_declaration` and `variadic_parameter_declaration`. Without
that, section 8's oracle for `int = 2` and `int = x` cannot be met, and the
release's own defect class survives inside its fix.

### Blast radius, predicted

| Prediction | Basis |
|---|---|
| **The oracles already exist.** Section 8 of `315_cpp_default_arguments.test` goes from `b, std::string, <e>, global, <e>` to `b, s, p, r, <e>`, and its control row from `<e>, <e>, a` to `q, r, a`. The file's own comment states this and says to rewrite the block, not re-record it | written yesterday for exactly this |
| `conformance/parameter_binding_multilang.test:184`, the `#317 / #318` C block, must be re-measured | it pins C's parameter names and types |
| Two fixture names change, from wrong to right | `test/data/cpp/*.cpp`: `const T& item` `T`->`item`, `const std::string& msg` `std::string`->`msg`. The other ten are already correct |
| `ast_definitions()` COUNTS should not move; CONTENT will | all 12 fixture parameter rows already have a non-empty name, so none enters or leaves the set. **Predicted, and the count must be measured both ways** |
| java does not move | its walk stops at `variable_declarator` and falls back. Oracle: `test/sql/languages/java_refinements.test` |
| C's `function_definition` gains a correct name for the nested-pointer case, `int` -> `fp_ret` | a free improvement from edit 3, which NO existing test covers, so it needs a new pin |
| **The three gate classes DO apply this time**, unlike #315 | edit 4 is a `.def` change, so the taxonomy, generated-reference and declared-strategy tables must each be measured |

### Order

Test first, as #315 did: rewrite section 8's block to the post-fix oracle and
add the C `fp_ret` pin, confirm both fail in the predicted places, commit red,
then implement. Plant one fault — the fallback left unsuppressed — and measure
that `int = x` returns to `x`, which is the assertion that proves edit 3's
suppression list does something.

**#317 is NOT collapsed by this.** Its subject is the parameter TYPE convention
differing between C and C++, which lives in C's own extractor. Only the name
half of C's defect is touched here, and only for `function_definition`.

## #186 decided — a root node is named by its path, literally

**Decided 2026-11-08.** Teague chose **the path exactly as given**, over a
basename, NULL, or a dotted import path, with the reason: a basename "will make
many files indistinguishable".

**That reason beats the argument I put against it.** I had said uniqueness is
not the name column's job, because `file_path` already provides it and names
collide everywhere else in the tree. That is true for a *definition* name and
wrong for a *scope* name: `:is-scope(module#utils)` matching two different
`utils.py` files is a selector that silently over-matches, which is this
release's own defect class — a plausible answer wrong in a way nobody sees.
`file_path` being a separate column does not help a query that has already
matched the wrong row.

### What was measured before asking

| | |
|---|---|
| Scope | **all 27 languages**, not Python's `module` alone: `program` (10), `source_file` (6), `document` (4), `translation_unit` (2), plus `chunk`, `stylesheet`, `config_file`, `compilation_unit`, `stream` |
| Current value | `''` on every one, **zero NULL** — so the issue's "`''` vs NULL" question is settled by measurement, not opinion |
| Where it is fixed | `src/include/unified_ast_backend_impl.hpp:288`, where `ExtractNodeName` is called and `file_path` is **already in scope** (used at :114, :216, :519). No adapter change, no `.def` change |
| What is already working | `scope.module` is an INT64 node reference, not a name, and it IS populated — 109 of 110 rows in `simple.py` point at node 0, the module node. The link resolves; only the name at the end of it is empty. The issue's framing of "`scope.module` lookups have nothing to match on" is slightly off |
| Why the dotted path was not chosen | the extension receives a path string, never a project root, so `pkg.sub.simple` needs per-language root discovery (`__init__.py`, `go.mod`, `Cargo.toml`) across 27 languages, and is impossible for `parse_ast`, which has no path |

### The blast radius, and why this does not land yet

**411 root rows in `test/data/**` would gain a name** — one per file parsed. That
is content churn on every `read_ast` call in the suite, and `name` is read by
`audit/name_extraction_audit.test`, `ast_copy_format.test`,
`ast_select_pseudo_classes.test` and `issue_212_count_field_widths.test` among
others.

So the implementation belongs **inside step 3, #288 with #276** — the accounting
pass — which the approved order already places before #186. Landing it first
would mean doing the accounting twice. The decision is what was needed now; the
code waits for the step that exists to absorb exactly this kind of churn.

### One sub-point, flagged rather than decided silently

`parse_ast` has no path and already carries the sentinel `file_path =
'<inline>'`. Taking the path literally means an inline parse's root is named
`<inline>`, so every inline parse shares one name. That is the same
indistinguishability objection, applied to sources that genuinely are not
distinct files — defensible, but it is a choice, and it is recorded here rather
than buried in the diff.
