# Sitting Duck v1.17.0

**Release date:** 2026-10-30

Names that were never bound, and 58 macros that can now describe themselves.

A correctness release. Four separate name-binding forms were invisible to
`ast_definitions()` and to the `NAME_DEFINITION` flag, so the same input now
returns MORE rows than v1.16.0 did. Nothing was removed, and no API changed
shape.

## New

**SQL macros carry descriptions and examples in `duckdb_functions()`**
(#170, #275). `duckdb_functions()` is the only surface an agent connected to a
database can read: the README and the registry's `extended_description` are not
reachable from SQL. The C++ functions already had descriptions; the SQL macros
had none, and that half of #170 had never been done.

Measured on this release candidate:

| kind | total | described | with examples |
|---|---:|---:|---:|
| `table_macro` | 52 | **52** | 12 |
| `macro` (scalar) | 45 | 6 | 1 |
| both | 97 | **58** | 13 |

Descriptions are not written in C++. They are lifted from the
`-- <name>: <summary>` banner that already sits above each macro in
`src/sql_macros/`, so a macro's documentation lives beside the macro and cannot
drift from it. Coverage is partial deliberately: most remaining comment blocks
are section headers covering a FAMILY of macros, and attributing one of those
to a single macro would populate the field while misdescribing the function.

**A derivation gate for native extractor dispatch** (#259, #271).
`scripts/verify_native_dispatch.py` asserts what a compiler cannot: every
node-type string an extractor dispatches on must appear in that grammar's
generated `ts_symbol_names[]`. #220 was three silent failures in three
languages, and none of them produced a compile error, a link error or a
warning.

Its first run found **29 dead branches in 9 languages** out of 768 dispatch
literals. On this candidate it reports **26 of 765** — the three the variadic
fix below removed. It carries a planted-fault self-test, which passes.

The gate is a script, not yet a CI step, and deliberately so: it exits
non-zero today. Most of the 26 are harmless redundancy, such as `cpp` also
dispatching on `pointer_type` beside live siblings, and none of them currently
fails a declared capability — the conformance kit reads `FAIL=0`. They are
latent, which is the condition #220 was in until a fixture happened to grow a
cell for it.

## Output changes

Four binding fixes. Each one makes `ast_definitions()` and the
`NAME_DEFINITION` flag return rows where v1.16.0 returned none.

| form | before | now | issue |
|---|---|---|---|
| `match x: case Point(y=1)` | capture bound nothing | capture binds | #279 |
| `[u for u in xs]` | comprehension shared the enclosing scope | comprehension is a scope boundary | #278 |
| `a, b = pair` | both leaves were `NAME_REFERENCE` | both bind | #274 |
| `for i, j in pairs` | both leaves were `NAME_REFERENCE` | both bind | #289 |

`for xx in items` already worked; the tuple form did not, and it is Python's
second most common binding form.

**Variadic parameters appear where the column was empty** (#220, #272). Native
variadic extraction was declared but dead in **go, cpp and swift**, so the
`parameters` column dropped the variadic entry. The derivation gate above is
what found it.

**Native extraction now dispatches in kotlin, lua and sql** (#256, #254,
#257). Each adapter declared a strategy that the grammar's actual node types
never reached, so declared capability delivered nothing.

## Fixes

- **A macro lost its description on Windows, and only on Windows.**
  `scripts/embed_sql_macros.py` read the `.sql` files with the locale's
  encoding. On a Windows runner that is cp1252, which breaks the em-dash banner
  separator at `src/sql_macros/ast_unparse.sql:525`, so
  `ast_unparse_exact_splice` never reached the documentation table. Reproduced
  on Linux by forcing the decode: 58 entries read as UTF-8, 57 as cp1252. All
  four opens now pass `encoding='utf-8'`, and the two decodings produce
  byte-identical headers.
- The deprecated lambda arrow (`->`) broke the #220 tests on the DuckDB 2.0
  line: a warning on v1.5.6, a hard Binder Error on 2.0 (#267). Test files
  only; the shipped SQL macros carry zero lambda-arrow uses, verified.
- The conformance kit's RAW-JOIN check is gated on the declared call-naming
  capability, so it stops reporting a gap a language never claimed (#253).

## Internal

- **A skipped test run now fails instead of reporting success** (#268). A green
  step is not a passing test: `ran tests: 0 passed, 127 skipped` is green and
  empty.
- Builds fire on push only for `main`; PR branches build through
  `pull_request`, so one commit no longer runs the matrix twice (#281).
- The generated language references are gated on their INPUT as well as their
  output, so a stale generated file cannot pass by matching itself (#285).
- The registry-pin check follows the registry's post-2.0.0 shape and stops
  reading a comment for data (#290), and the v2.0 coverage leg is pinned to the
  `v2.0.0` tag rather than the moving `v2.0-cyanoptera` branch (#291, #266).

## Known issues

- **`ast_select` is 28x slower on the DuckDB 2.0 line.** Measured on this
  release's source, built against the released `v2.0.0` tag and against
  `v1.5.6`, through the same dynamic load and the same fixture: 0.448 s per
  call on v1.5.6, 12.537 s on v2.0.0. The cost is flat in input size (a
  one-row table still takes 12.717 s) and flat in selector complexity
  (`.func:has(.call)` takes 12.663 s), so it is planning, not row
  processing. It is an upstream planner regression, `duckdb/duckdb#26036`,
  reported by us. It no longer reproduces on duckdb `main`, and that fix is
  in no release yet.

  The registry's default build (`ref`) targets the 2.0 line, so an install on
  DuckDB 2.0 pays this today. `variegata` keeps a v1.5.6-buildable commit, so
  only the v1.5.6 artifact is unaffected.

  **The cost is planning, measured, not execution.** Under `EXPLAIN ANALYZE`
  every operator reports 0us on both lines; the only non-zero timing is the
  query total. So execution is free and essentially all of the 12.5 s is
  bind, plan and optimize. The v1.5.6 side behaves the same way at 0.463 s,
  which makes the planning ratio about 27x.

  Do not read `EXPLAIN` wall time as planning time. `EXPLAIN` takes 71.2 s
  against 0.615 s, which is larger than the whole query, because it also
  renders the plan: 11 MB of text against 685 KB on v1.5.6.

  **Upstream `main` is 10.5x faster, and the tag that ships is not.** Built
  against duckdb `main` at `ed0443f18a` with this release's source unchanged,
  the same call costs **1.192 s** rather than 12.537 s. That is 2.6x v1.5.6
  rather than 28x. `main` is 2,312 commits past the `v2.0.0` tag. Which
  commit is responsible is not identified. It is not `duckdb/duckdb#27757`,
  the first candidate its description suggested: the commit before it,
  `dac82746fe`, already runs the same call in 1.234 s.

  The plan shape does not change: 113 Cross Products, 69 CTEs and 205
  materialized-consumer sites on both builds. So the improvement comes from
  planning this shape more cheaply, not from a different plan. No change to
  `css_selectors.sql` is needed to get it.

  **One half of the problem is not fixed.** Prepared statements still re-pay
  the whole cost on the 2.x line:

  | | `PREPARE` | `EXECUTE` x3 | amortizes? |
  |---|---|---|---|
  | v1.5.6 | 0.329 s | 0.117 / 0.111 / 0.118 s | yes, 2.8x cheaper |
  | `v2.0.0` tag | 12.530 s | 12.664 / 12.671 / 12.645 s | no, 0% saved |
  | `main` `ed0443f18a` | 1.260 s | 1.226 / 1.344 / 1.273 s | no, 0% saved |

  "Prepare once, execute many" buys nothing on either 2.x build. Against
  v1.5.6's prepared 0.117 s, the residual on `main` is about 11x. That part
  belongs to `#26036`, which is still open.
- **39 of the 45 scalar macros still have no description.** They need a banner
  written beside them, which is content work tracked on #170.
- **Go `for k, v := range xs` deliberately binds nothing.** It has the same
  shape as the Python form fixed here, but `:=` binds while `=` reassigns, so
  its left leaves are not unconditionally definitions. That is #277's decision,
  and the test asserts Go binds nothing so the expectation must change
  deliberately.
- **#288 still hides some flagged names.** `ast_definitions()` filters on the
  definition-kind semantic type, so a name can carry the `NAME_ROLE` flag and
  not appear through the public macro.

## Upgrading

No API removals. Two things to check:

1. **If you pin counts from `ast_definitions()`, or count `NAME_DEFINITION`
   flags**, re-measure. The four binding fixes above add rows for Python
   match/case captures, comprehension targets, destructuring targets and
   for-loop tuple targets.
2. **If you read the `parameters` column for go, cpp or swift**, variadic
   entries now appear where the column was previously short one entry.

If you relied on an empty `description` in `duckdb_functions()` for SQL macros,
58 of them are now populated.

## Verification

Measured on the release candidate, not carried over from the branch runs:

- Test suite, run with `SITTING_DUCK_TEST_GRAMMAR_DIR` set so **nothing is
  skipped**: `All tests passed (9335 assertions in 167 test cases)`, and zero
  skip lines in the output. A plain `make test` skips five runtime-grammar
  files, which is what the shipping CI legs do: they report 162 cases with 5
  skipped, and 162 + 5 = 167.
- Conformance kit: `ok=192 FAIL=0 dirty=1 void=7 UNDECL=5 n/a=19`, 28 of 28
  languages, no language without a fixture. v1.16.0 shipped with `ok=189
  FAIL=3`; those three FAILs were the #220 kotlin, lua and sql dispatch bugs,
  and they are gone.
- Three declaration gates clean: **0 unreachable of 3698 declarations** (7 more
  are unreachable for one language but needed by a sibling that shares the
  `.def`), **60 declared anonymous-token collisions with 0 gaps** across 27
  languages, and **0 identical / 0 differing** shadowed declarations across the
  one include edge.
- The new native-dispatch gate reports **26 dead branches of 765 dispatch
  literals** across 20 extractors and exits non-zero, which is its designed
  behaviour rather than a regression; its planted-fault self-test passes
  (`self-test OK: plants a dead dispatch and detects exactly it; ignores text
  comparisons`).
- Macro documentation, read from the built extension: 97 macros in the
  `memory` catalog, 58 described, 13 carrying examples; DuckDB's own 131 core
  macros remain undescribed and untouched.
- Registry-side CI on the merge commit: run `40626001782` on `main` is
  `completed/success` with no job outside success and skipped, and both Windows
  legs — MSVC and mingw — report `All tests passed (5 skipped tests, 9027
  assertions in 162 test cases)`. mingw had never been measured before this
  cycle; fail-fast cancelled it every previous time.
